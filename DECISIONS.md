## ADR-0024: Repo and pipeline scaffolding runs on two GitHub Apps, a dedicated organization, and keyless image publishing

Status: Proposed, design approved for build 2026-10-02 (decisions: organization idp-platform-apps, scaffolded repositories public only, the service runs the image its own pipeline builds)

Context. The Goal promises "a repo, a pipeline, cloud infrastructure, and a catalog entry". v1 delivers the last two through a reviewed pull request (CLAUDE.md, v1 scope). The first two were deferred in ADR-0022 for two reasons: creating repositories needs a credential far broader than the single-repository token in ADR-0019, and every scaffolded repository's CI draws on Actions minutes, which already ran out once (October usage hit 2,001 of 2,000 free minutes and stopped every job until the $10 Actions budget existed). Phase 6 closes that gap, and a pipeline only counts if what it builds is what runs. Facts this design rests on, each checked in source, in GitHub's or AWS's documentation, or read-only against the account on 2026-10-02 rather than assumed:

- The image already has what it needs. backstage/app/packages/backend registers @backstage/plugin-scaffolder-backend-module-github (0.10.0 in yarn.lock), and its credentials come from @backstage/integration 2.1.2, which reads integrations.github[].apps[] with appId, privateKey, clientId, clientSecret, an optional webhookSecret, allowedInstallationOwners, and publicAccess. GitHub App auth is therefore configuration plus a Secret, with no image rebuild.
- Backstage mints installation tokens per owner, caches each until ten minutes before its one-hour expiry, and requests them without narrowing repositories or permissions, so a token carries everything the installation has.
- When an installation is on selected repositories, Backstage lists them and refuses a token for any repository not on the list. A repository the scaffolder is about to create cannot be on the list, so creating repositories needs an installation on all repositories of its owner.
- When no App yields a token for an owner and repository, Backstage silently falls back to integrations.github[].token. A PAT left in config is a live fallback, not a spare.
- Creating a repository, archiving it (PATCH), deleting it, and setting branch protection all require the same App permission, Administration write, and GitHub offers no narrower split. An App that can create repositories can delete every repository it is installed on.
- Pushing a file under .github/workflows requires the Workflows permission in addition to Contents.
- jordann6 is a personal account on GitHub Free holding 63 repositories. Branch protection on GitHub Free is available only on public repositories, and rulesets for repositories in an organization need GitHub Team. Actions minutes are charged to the repository owner, standard hosted runners are free on public repositories, and an organization on GitHub Free has its own 2,000 minutes and its own budget. The name idp-platform-apps is unclaimed.
- platform-guardrails is public, so any repository can call its reusable workflows. Its floating v1 tag points at 7d3f799, which is older than v1.4.0 (f3ac73c); ci.yml exists at both. ci.yml builds and scans an image but publishes nothing.
- GHCR is the wrong registry for this platform. A package's first publish is private even when its repository is public (it inherits access permissions, not visibility), and GitHub Packages authenticates pulls only with a classic personal access token, the long-lived, person-bound kind of credential this phase removes. Each cloud's cache would also need that token stored in a cloud secret.
- ECR Public is the right one. All three runtimes already pull public.ecr.aws without any credential (the ECR pull-through cache, the Artifact Registry remote repository ecr-public, and the ACR cache rule, ADR-0022), and every Composition already accepts and rewrites public.ecr.aws references. The account has no ECR Public repository yet, and ECR Public offers no lifecycle policy operation. The account already holds an IAM OIDC provider for token.actions.githubusercontent.com, created outside this repository's Terraform.
- The scaffolder has no built-in action that edits a file in an existing repository; fetch:template renders whole files from values. Updating a claim's image therefore needs every other claim value from somewhere other than the claim file.

Decision.

Owner. Scaffolded repositories live in a new GitHub organization, idp-platform-apps, on the Free plan, not in the jordann6 account. Creating repositories requires an all-repositories installation (above), and an all-repositories installation on jordann6 would hand Administration write, and so delete, over all 63 personal repositories and idp-platform itself to whoever holds the App's key. An organization makes "all repositories" mean only repositories the platform created. jordann6 is its only owner. Creating it is a browser step with no standing cost. Its settings are applied by gh api calls, not the console: secret scanning push protection is on for every new public repository, and the OIDC subject template is pinned to GitHub's immutable format, which carries the organization's numeric ID (see Image publishing). Members cannot be barred from deleting repositories through the API on this plan; see build step 2.

Two GitHub Apps, so the credential that can delete repositories is never installed where the platform's own code lives:

- idp-platform-gitops, installed on the jordann6 account, selected repositories, idp-platform only. Permissions: Contents read and write (push the claim branch), Pull requests read and write (open the claim pull request), Commit statuses read (the URL reader resolves a ref through the commit status API before it fetches a skeleton, the 403 found in ADR-0019), and Metadata read (mandatory). It does exactly what the PAT does today, for the Database and WebService templates, the two new templates' claim pull requests, and the catalog Location.
- idp-platform-scaffolder, installed on the organization, all repositories. Permissions: Administration read and write (create the repository and set branch protection), Contents read and write (the initial push), Workflows read and write (the initial push carries .github/workflows/ci.yml), and Metadata read. Nothing else: no Members (CODEOWNERS names users, and no team or collaborator is added), no Secrets or Variables (nothing is stored in the repository), no Actions, no Packages, no Pull requests, no organization permissions.

Both Apps are private (installable only on the account that owns them), have no webhook (Backstage is reached only through a localhost port-forward, ADR-0019), and do not request user authorization during installation. Each App entry in integrations.github sets allowedInstallationOwners to its one owner, so even a wrongly placed installation is never used. Backstage routes by owner: claim pull requests target jordann6/idp-platform and get the gitops App's token, and repositories are created under the organization with the scaffolder App's token.

The PAT is removed, not kept as a fallback. integrations.github loses its token field, make backstage-token and the backstage-github Secret are deleted, and the PAT is revoked in the browser instead of rotated. Because Backstage falls back to the token silently, keeping it would mean a misconfigured App keeps working on the person-bound credential and nobody notices. Without it, a misconfiguration fails the scaffolder step with "No token available", which is the signal wanted. The existing templates need no change, since their repoUrl is unchanged and only the credential behind it moves.

Private keys. Each App's private key, app ID, client ID, and client secret (the config schema requires the last two even though installation tokens never use them) live in ~/.config/idp-platform as github-app-gitops.* and github-app-scaffolder.*, mode 600, never committed. A new make backstage-github-apps target loads them into one Secret, backstage-github-apps, refuses to run if any file is missing or not mode 600, and Helm values reference its variables in place of GITHUB_TOKEN. A private key never expires, which is the trade for one-hour tokens, so rotation is procedural: generate a second key in the App settings (GitHub allows several active keys and has no API to create one), save it with the clipboard-wait command, run make backstage-github-apps, restart Backstage, confirm one template step mints a token, then delete the old key in the browser. Rotation happens every 90 days and immediately on any suspected exposure, and deleting a key revokes it at once, which is the incident response the PAT never had. Keys stay on this Mac and in one Kubernetes Secret, the same storage tier ADR-0018 accepted for the Argo deploy key; moving them into a cloud secret store waits with the External Secrets deferral in ADR-0002.

Image publishing. Each scaffolded repository publishes its own image to ECR Public with no stored credential anywhere, and the existing caches carry it to every cloud unchanged.

- A new Terraform root, bootstrap/aws/ci-publish, reads the existing GitHub OIDC provider as a data source (it does not create or adopt it) and creates one role, idp-ci-publish, under the platform's permissions boundary. Its trust requires audience sts.amazonaws.com and a subject matching repo:idp-platform-apps@<organization ID>/*:ref:refs/heads/main, GitHub's immutable subject format, so the trust is bound to the organization's numeric ID, not only to a name that could be released and claimed by someone else. Repository names and git refs cannot contain a colon, so the wildcard cannot reach into the ref. (Amended at build step 2: the design first called for a custom subject template of repository_owner_id, repository, and ref; see that step for why.) Only main can publish; pull request runs build and scan but never push.
- Its policy grants ecr-public:GetAuthorizationToken and sts:GetServiceBearerToken (which accept no resource scope), and on repository/idp-platform-apps/* only: CreateRepository, DescribeRepositories, DescribeImages, BatchCheckLayerAvailability, InitiateLayerUpload, UploadLayerPart, CompleteLayerUpload, PutImage, and TagResource, with creation requiring the Project and Team tags where ECR Public supports request tag conditions (confirmed with iam simulate-principal-policy before apply). No delete, no repository policy changes, nothing outside the prefix. Standing cost is zero: the role is free, and ECR Public storage is free up to 50 GB a month.
- The role ARN carries the account ID, which this repository keeps out of git (ADR-0018), and scaffolded repositories are public, so it is not in any skeleton either. make ci-publish sets it as an organization Actions variable from Terraform outputs with gh variable set --org. configure-aws-credentials masks the account ID in logs by default.
- The skeleton's workflow has a publish job on pushes to main only, after the guardrails checks pass. It assumes the role through OIDC, creates public.ecr.aws/<alias>/idp-platform-apps/<team>.<name> on first use, builds linux/amd64 and linux/arm64 with buildx (Fargate runs ARM64, Cloud Run and Container Apps run the amd64 entry, ADR-0022), pushes, and writes the full digest reference to the job summary. The image carries the org.opencontainers.image.source label, so the catalog, the registry, and the repository point at each other. Every third-party action in the skeleton is pinned by commit SHA.
- The registry alias is assigned by AWS when the first ECR Public repository is created and cannot be chosen without a console request. It is not a secret; it is recorded in the deploy template after the first publish, as a reviewed change.

What the templates create. Two new templates under backstage/templates deliver all four parts of the Goal, and running the repository's own image takes one more reviewed pull request, because the first build finishes after the scaffolder run has ended.

service creates the repository, its pipeline, the cloud infrastructure, and the catalog entry in one run:

- A repository named <team>.<name> in the organization, for example team-demo.web-a. Team names and service names cannot contain dots, so the dot makes the name unambiguous, which a hyphen would not be (team-demo plus x-y and team-demo-x plus y would collide, the problem ADR-0022 hit with ALB host names). It is public, with wiki and projects off, squash merge only, and branches deleted on merge. Topics carry the team and idp-platform.
- A skeleton holding a README, a Dockerfile built FROM the same digest-pinned public.ecr.aws/nginx/nginx-unprivileged index every WebService proof ran, a static page that names the repository (so the repository's own image is visibly different from the base image), CODEOWNERS, and .github/workflows/ci.yml. That workflow calls jordann6/platform-guardrails/.github/workflows/ci.yml pinned by full commit SHA (v1.4.0, f3ac73c), never by the floating v1 tag, which is stale today, then runs the publish job above. The guardrails workflow detects the stack and runs gitleaks over full history, builds the image and scans it with Trivy, and audits Node, Python, or Go dependencies when present. tf-ci.yml and finops-gate.yml are for Terraform roots and do not fit a service repository; they are not called.
- Branch protection on main through publish:github's protectDefaultBranch, applied after the initial push: pull requests required, the two always-run checks required (the gitleaks job and the stack detection job, named <caller job> / <called job>; exact contexts confirmed on the first live run), branches up to date, and admins included. Required approvals are zero and code owner review is off, because every scaffolded repository has a single human (jordann6), who cannot approve their own pull request, so requiring one would lock the branch. CODEOWNERS still names the owners. Rulesets are not used: the GitHub module drives only the classic branch protection API, and organization rulesets need GitHub Team.
- CODEOWNERS lists the GitHub usernames of the team Group's members, from the hasMember relations catalog:fetch returns. User entity names equal GitHub usernames because sign-in resolves by name (ADR-0019), so no mapping table exists.
- In the same run, a pull request on idp-platform carrying the WebService claim and one Component entity. The entity is the existing <name>.webservice.yaml Component with github.com/project-slug and backstage.io/source-location pointing at the new repository, so the running service and its repository are one catalog entry, and the claim and entity pairing check (ADR-0019) applies unchanged. The catalog entry stays in the platform's git rather than as a catalog-info.yaml registered from the new repository, so the catalog shows what was approved (ADR-0019), and the scaffolder App never needs to be read by the catalog. The entity also carries every WebService value as platform.jordandesigns.io annotations (port, health path, size, visibility, maximum instances, environment, cost center, and the image), because the deploy template must re-render the claim without being able to edit it. The claim's first image is the skeleton's base digest, which is already proven on all three clouds and lets the service come up before the repository's first build has finished.

The service template's output links the repository and the pull request. The repository is created before the pull request, so a reviewer sees a real repository and its first CI run while deciding whether to merge the cloud half.

deploy moves a service onto an image its pipeline built. The developer picks the service's Component and pastes the digest from the publish job's summary. The template accepts only sha256:<64 hex>, builds the reference itself as public.ecr.aws/<alias>/idp-platform-apps/<team>.<name>@<digest> from the Component's own repository annotation, so a service cannot be pointed at another repository's image through this path, re-renders the claim and the entity from the entity's annotations with the new image, and opens a pull request. Deploying is therefore a reviewed, digest-pinned change like every other change to a claim, and rolling back is the same template with the previous digest. scripts/check-claim-entities.sh is extended to fail when an entity's annotations and its claim disagree, so a claim edited by hand cannot drift silently from the values the deploy template will render.

Actions minutes. Scaffolded repositories are public, which makes their CI free on standard runners and is also what makes branch protection available on GitHub Free. Minutes are charged to the owner, so scaffolded repositories never touch jordann6's 2,000 minutes or the $10 budget; idp-platform's own CI is unaffected by any number of scaffolded repositories. The organization gets no payment method, so its budget is effectively zero with usage stopped: if a repository were ever made private and burned the organization's 2,000 minutes, its jobs would stop and nothing would be billed or spill into the personal account. Each scaffolded workflow runs on pull requests and on pushes to main only, ignores documentation-only pushes to main (paths-ignore for *.md and docs/**; pull requests always run, see build step 4), and sets concurrency per ref with cancel-in-progress, so a stream of pushes runs once; the publish job uses a concurrency group that does not cancel, so a push to main is never half published. No schedule, no Dependabot version updates (each would open pull requests that each run CI), and no matrix. The arm64 half of the build runs under QEMU emulation, which is slow for compiled code but costs nothing on public repositories; a skeleton with a compile step would move to native arm64 runners instead. Public repositories make the source visible, which suits a portfolio platform and a skeleton that holds nothing secret; there is no private option in the template, and adding one is a reviewed change that must answer the minutes and branch protection questions again.

Teardown. Three halves, each with its own credential, none of them the portal's. The cloud half is unchanged: a pull request on idp-platform removes the claim and its entity, followed by one explicit prune sync when it is the team's last (ADR-0018). The repository half is done by a person: gh repo archive by default, which is reversible and stops all workflows, or gh repo delete for a full teardown such as the live proof. Deletion uses jordann6's own gh credential with the delete_repo scope added for that command and removed afterwards (gh auth refresh -s delete_repo, then gh auth refresh --remove-scopes delete_repo). The image half is make ecr-public-clean SERVICE=<team>.<name>, which deletes the ECR Public repository with the local AWS credential, since the publish role holds no delete. The scaffolder App does hold delete on repositories, because GitHub ties it to the Administration write that creation needs; that capability is contained rather than removed:

- It reaches only repositories in the organization, never idp-platform or any personal repository.
- No installed scaffolder action deletes or archives a repository: the GitHub module has none, and no generic HTTP action is installed. Templates are reviewed pull requests to this repository, so adding such an action is itself a reviewed change.
- The key never leaves the Mac and the backstage Secret, and deleting it in the App settings revokes it at once.

A script, scripts/check-scaffolded-repos.sh, compares organization repositories, ECR Public repositories under the prefix, and Component entities, and lists any of the three without the others, so an abandoned half is found rather than forgotten.

Leaks and trade-offs.

- The App that creates repositories can delete them. GitHub has no create-only permission. The two-App split and the dedicated organization bound the damage to platform-created repositories.
- Repository creation forces an all-repositories installation, because Backstage checks a token against the installation's repository list before the repository exists. This is the reason for the organization, not a preference.
- The publish role cannot be bound to one ECR repository per GitHub repository: IAM cannot turn the OIDC subject into a resource path, so any repository in the organization publishing from main can push to any repository under the prefix. What runs is still decided by the digest in a reviewed claim, and the deploy template only builds references to the service's own repository, so a stray push changes nothing that is deployed. Per-repository roles would close it at the cost of a Terraform change per service, which defeats self-service.
- A service runs its own image one pull request after it exists, not in the same run. The scaffolder cannot wait for a CI run to finish, so the first claim runs the base image and the deploy template promotes the built digest. The upside is that every image change, the first included, is a reviewed digest.
- The claim's values live twice, in the claim and as annotations on its entity, because the scaffolder cannot edit a file in place. The pairing check now compares them. A custom scaffolder action that edits the claim would remove the duplication but adds platform code to the Backstage image and a rebuild per change, so it is not taken now.
- ECR Public has no lifecycle policy, so every push to main adds an image that stays until the repository is deleted. The 50 GB free tier covers well over a thousand pushes of the skeleton; a long-lived service would need a pruning job with delete rights, which this design deliberately withholds from CI.
- ECR Public lives only in us-east-1 and its alias is random, so image references read public.ecr.aws/<random alias>/..., not a platform name. A custom alias needs a console request, which the CLI-only convention in CLAUDE.md leaves out.
- The GitHub OIDC provider in the account was created outside this repository. bootstrap/aws/ci-publish reads it rather than owning it, so deleting it elsewhere would break publishing; the dependency is recorded in that root's README.
- The scaffolder run is not a transaction. If the claim pull request fails after the repository exists, the repository stays and the run reports failure; rerunning with the same name fails at creation because the repository exists. The orphan check script and a manual delete are the recovery.
- Commits and pull requests are authored by the Apps' bot identities, not the requester. The requester stays in the pull request body and on the entity's requested-by annotation, as today, but GitHub's audit trail shows the bot.
- Branch protection with zero approvals is a single-maintainer compromise. With a second human in the Group the template would require one approval and code owner review; that is a parameter, not a redesign.
- A reusable workflow's caller cannot set timeout-minutes, so a hung guardrails job runs to GitHub's six-hour default. On public repositories that costs nothing; adding a timeout input to platform-guardrails is the fix if private repositories are ever offered. The publish job is the skeleton's own and sets a timeout.
- Public by default exposes everything a team commits. gitleaks in CI is detective, not preventive, so a secret pushed to a scaffolded repository is public until history is rewritten; push protection is the preventive layer. The images are public too, which is the price of credential-free pulls.
- On GitHub Free, the API silently ignores the setting that stops members deleting or transferring repositories (build step 2). With a single owner and no other member it protects nothing, so it is left on rather than set in the console; adding a member who is not an owner must include turning it off.
- The platform now depends on two GitHub Apps and an organization created in a browser. Their exact settings are recorded here so they can be recreated, but they are not in Terraform: the GitHub provider can manage repositories and protection but cannot create an App, an organization, or a private key.
- Backstage still runs on a laptop behind a port-forward, so the Apps receive no webhooks and the catalog does not see a repository until the claim pull request merges and the Location refreshes.

Build order, each module with its own verification checklist, after the organization and both Apps exist:

1. Credentials: make backstage-github-apps, Helm values switched to the two Apps and the token removed, Backstage reinstalled. Check that the catalog still reads main, the Database and WebService templates open a pull request as the gitops bot (closed unmerged), and Backstage has no GITHUB_TOKEN in its environment. Then the PAT is revoked.
2. Organization settings by gh api: members cannot delete repositories, push protection on, OIDC subject template set; each read back. (As run, the subject template is the immutable default and member deletion is a recorded gap; see build step 2 below.)
3. bootstrap/aws/ci-publish with the full Terraform checklist (fmt, validate, tflint, Checkov, Trivy, conftest against platform-guardrails main, lock hashes for linux_amd64 and darwin_arm64, a guardrails.yml job and a ci-changed-roots.sh entry), iam simulate-principal-policy for allowed and denied pushes, creates, and deletes, then make ci-publish for the organization variable.
4. Templates: service and deploy, the skeleton and its workflow, CODEOWNERS rendering, the extended pairing check, and the orphan check script.
5. Live proof as jordann6 on team-data (GCP, which has no per-session ingress cost): run service, see the repository with protection and CODEOWNERS, see its first CI run pass and publish a two-architecture image to ECR Public, merge the claim pull request on an all-pass and see the WebService Ready on the base image with its catalog entry and source link, run deploy with the published digest, merge, and see the URL serve the repository's own page. Then tear all three halves down and confirm GitHub, ECR Public, GCP, and the catalog are empty. Results are recorded here and the status flips to Accepted.

Setup and build step 1, 2026-10-02. The organization (idp-platform-apps, Free plan) and both Apps exist as specified, each read back through the API: idp-platform-gitops (owned by jordann6) holds contents and pull requests write and statuses and metadata read, with no events, on an installation limited to jordann6/idp-platform; idp-platform-scaffolder (owned by the organization) holds administration, contents, and workflows write and metadata read, with no events, on an all-repositories installation. Each private key was checked against the fingerprint GitHub shows and then exercised by signing a JWT and minting an installation token, which was revoked straight after: the gitops installation listed exactly one repository, and the scaffolder installation listed none and got 404 on jordann6/idp-platform, so the App that can delete repositories cannot reach the platform's own. make backstage-github-apps refused a missing file and a file in mode 644 before touching the cluster, then loaded the eight values into backstage-github-apps and deleted the PAT Secret. After the Helm upgrade, the Backstage pod had the App variables and no GITHUB_TOKEN. The first catalog read of main failed once with "fetch failed" seconds after the VM booted, before cluster DNS was ready, and did not recur; the signed-in portal then listed all four Groups and both templates, read through the gitops App alone. The Database and WebService templates, run as jordann6, opened PRs #59 and #60 authored by idp-platform-gitops[bot] with bot-authored commits; both claims (owner jordann6, cloud aws from the team) passed a server dry run, and both pull requests were closed unmerged. The WebService run used visibility public, because team-demo is on AWS, where deny-internal-webservice-aws refuses internal.

Build step 2, organization settings, 2026-10-02. Each setting was applied with gh api under a temporary admin:org scope and read back, and a throwaway public repository, idp-platform-apps/oidc-probe, was created to see what a new repository actually gets, then deleted.

- Push protection. The organization-level fields for it are being retired in favor of code security configurations, so a configuration, idp-platform-push-protection, turns on secret scanning and push protection, leaves CodeQL default setup and Dependabot alerts off (each would add runs or pull requests to every repository), is enforced so a repository administrator, the scaffolder App included, cannot turn it off, and is the default for new public repositories. GitHub refused the configuration with 400 until advanced_security was enabled in it, although secret scanning on public repositories costs nothing either way. The probe repository had both features enabled about twenty seconds after it was created, with the configuration attached as enforced.
- OIDC subject. The custom template was set as designed and read back, but the probe showed it would never apply: a new repository does not inherit an organization template (its customization reads use_default true, and opting in is a separate call per repository), and new repositories already default to GitHub's immutable subject. A workflow on the probe's main branch printed sub repo:idp-platform-apps@337025991/oidc-probe@1402134644:ref:refs/heads/main, which carries the organization's numeric ID, the property the custom template existed to add. Keeping the template would have needed every scaffolded repository opted in, and no scaffolder action does that, so the trust uses the default subject instead (Image publishing above). GitHub has no call that deletes an organization template and refuses an empty one, so the template is now repo and context with use_immutable_subject true, which produces the default subject: with the probe opted in, the next run printed exactly the same sub. A repository that opts in therefore cannot change what the trust sees.
- Member deletion, a recorded gap. PATCH /orgs with members_can_delete_repositories false returned 200 and changed nothing: the organization still read true, and updated_at did not move, whether the value was sent as a JSON boolean, a string, or a raw body. The setting exists in the organization's settings page, but this platform takes no console steps, so it stays at true. It protects nothing today: jordann6 is the only member and an owner, owners can always delete and transfer, and the setting does not govern the scaffolder App, whose delete capability comes from Administration write and is contained as described under Teardown. It starts to matter when a second member who is not an owner joins, and turning it off becomes part of adding that member.

Build step 3, bootstrap/aws/ci-publish, 2026-10-02. The root reads the account's existing GitHub OIDC provider (audience sts.amazonaws.com, already used by three unrelated roles) with a data source and creates four resources: the idp-ci-publish role, its policy and attachment, and a boundary of its own, idp-ci-publish-boundary. The Crossplane provider's boundary was not reused, because adding ECR Public to it would have widened the ceiling on the provider role as well. The new boundary allows only ECR Public and sts:GetServiceBearerToken, denies every region but us-east-1 (ECR Public's API exists only there), and explicitly denies BatchDeleteImage, DeleteRepository, DeleteRepositoryPolicy, SetRepositoryPolicy, and UntagResource, so a later widening of the identity policy still cannot remove an image. The trust is audience sts.amazonaws.com and StringLike subject repo:idp-platform-apps@337025991/*:ref:refs/heads/main. ECR Public's service authorization reference lists aws:RequestTag and aws:TagKeys only on CreateRepository and TagResource, so those two carry the tag conditions (Project idp-platform, Team team-*, no other keys); the push and describe actions are scoped to repository/idp-platform-apps/* only, and ECR Public repository ARNs carry no region. The bearer token is limited by sts:AWSServiceName to ecr-public.amazonaws.com. Checkov flagged the two token actions as credential exposure (CKV_AWS_107), which is the purpose of a push role, so that check is skipped with the reason in the code. Every gate passed locally and in CI: fmt, validate, tflint, Checkov (40 passed, 4 justified skips), Trivy, conftest against platform-guardrails main (34 of 34), and lock hashes for linux_amd64 and darwin_arm64. iam simulate-custom-policy on the planned documents, then simulate-principal-policy on the applied role, gave the same 30 results: create and tag with the right tags on the prefix, each push and describe action on the prefix, the auth token, and the ECR Public bearer token were allowed; create without tags, with another Project, with Team platform, with Team missing, or with an extra Owner key, create or push outside the prefix, tagging with another Project, catalog data changes, a bearer token for another service, and private ECR, IAM, and S3 calls were implicitly denied; every delete, untag, and repository policy change, and a push from us-west-2, were explicitly denied by the boundary. The simulator proves the policy logic, including that the tag conditions are evaluated on create; that ECR Public enforces them at call time, and that the trust accepts a real token, are shown by the first publish in build step 5. The apply created exactly four resources and a fresh plan was empty. make ci-publish set the organization Actions variable IDP_CI_PUBLISH_ROLE_ARN (visibility all) from the Terraform output, and the value read back equal to the output; the account ID stays out of git and out of every skeleton. Standing cost is zero.

Build step 4, templates and checks, 2026-10-02. backstage/templates/service holds the template and three skeletons (the repository, the claim, and the entity); backstage/templates/deploy reuses the claim and entity skeletons through ../service, so there is one definition of each file. Both are registered in the catalog Location. The repository skeleton is a README, a Dockerfile FROM the pinned nginx-unprivileged index that copies site/ into the web root, a page naming the repository, CODEOWNERS, and .github/workflows/ci.yml. The workflow calls platform-guardrails ci.yml at f3ac73cfd5dcc2d13491b6997c4796b1eb1c8656 with security-events write (the called workflow uploads SARIF), and on pushes to main a publish job assumes idp-ci-publish through vars.IDP_CI_PUBLISH_ROLE_ARN, finds or creates the ECR Public repository named exactly like the GitHub repository and tagged Project and Team (the team is the part of the name before the dot), builds linux/amd64 and linux/arm64 under QEMU with provenance off so the index holds exactly the two platform images, labels the image with its source repository, and writes the digest and full reference to the job summary through environment variables rather than inline expressions. All six actions are pinned by full commit SHA with the release in a comment (checkout v7.0.1, configure-aws-credentials v6.3.0, amazon-ecr-login v2.1.7, setup-qemu-action v4.4.0, setup-buildx-action v4.4.1, build-push-action v7.4.0). The workflow is copied without templating, because GitHub's expressions use the scaffolder's own delimiters. Four details came from reading the scaffolder source rather than its documentation:

- publish:github defaults to a private repository, one required approval, and merge and rebase commits allowed, so the template sets every one of those explicitly: public, zero approvals, squash only, branches deleted on merge, wiki and projects off, enforce admins on, branches up to date, and the two required contexts guardrails / Detect stack and guardrails / Secret scan (gitleaks), named <caller job> / <called job name>; the exact strings are confirmed on the first live run.
- When applying branch protection fails, publish:github logs "Skipping: default branch protection" as a warning and the run still succeeds. A green scaffolder run therefore does not prove the branch is protected, so the live proof reads protection back from the API.
- Required checks and paths-ignore conflict. A pull request that changed only documentation would not run the workflow, the required checks would never report, and the pull request could never merge. The design said documentation-only changes skip CI; as built, only pushes to main skip them, and every pull request runs. On public repositories that costs nothing.
- publish:github accepts an oidcCustomization input that sets the repository's subject template. It is not used: the immutable default subject is what the trust expects (build step 2), and a repository that opted in would get the same subject anyway.

The deploy template builds public.ecr.aws/<alias>/<repository annotation>@<digest> from a constant alias. Until the first publish assigns the alias, the constant is ALIAS_UNSET, which contains capitals, so the XRD rejects any claim rendered from it; a server dry run of such a claim was refused, and the same claim with a lowercase alias was admitted. Setting the real alias is a one-line reviewed change in build step 5. The deploy template's Component picker offers only Components carrying the repository annotation, so services from the plain WebService template are not offered.

scripts/check-claim-entities.sh now also compares, for every entity with the repository annotation, eleven values against the claim: image, port, health path, size, visibility, maximum instances, environment, cost center, owner (requested-by), cloud label, and namespace (team). Values are read as text, since both files are template output with one key per line, and a value that cannot be read counts as a mismatch. scripts/check-scaffolded-repos.sh lists every <team>.<name> missing from any of the organization's repositories, the ECR Public repositories under idp-platform-apps/, and the catalog entities, and exits 1 if any is. make ecr-public-clean SERVICE=<team>.<name> deletes the ECR Public repository and its images with the local credential, refusing anything not shaped like team-<x>.<name>.

Verified offline, with no cloud or GitHub change. The three skeletons were rendered with the same engine and default filters fetch:template uses (nunjitsu and the scaffolder's parseEntityRef and pick): CODEOWNERS listed only the hasMember users from a mixed relations list, the page and README named the repository, and the workflow came out byte-identical to the source. The rendered service claim passed a server dry run for team-data; the deploy render differed from it only in the image line, and the pairing check passed on both. What only the live run can prove: the template-level expressions (the team's relations passed to the skeleton, the deploy template's relative skeleton paths, the picker's annotation filter), the protection and required contexts GitHub actually stores, the first publish through the trust, and ECR Public's tag enforcement.

Consequences. The Goal is met end to end: one portal run produces a repository with a passing pipeline, a reviewed pull request for the cloud infrastructure, and one catalog entry that ties them together, and the image that pipeline builds reaches whichever cloud the team uses through a second reviewed pull request. No long-lived credential is added anywhere: Backstage uses one-hour installation tokens, CI publishes through OIDC, the clouds pull anonymously through the caches they already had, and the person-bound PAT disappears. A key compromise has a bounded blast radius and a one-click revocation. Scaffolded CI and image storage cost nothing and cannot exhaust the minutes the platform's own CI needs, so the platform's standing cost is unchanged.

## ADR-0023: Admission policies are Kyverno ValidatingPolicies, each tied to a control and a test

Status: Accepted (validated live 2026-10-02)

Context. Phase 5 makes compliance a property of the paved road (ADR-0005): a non-compliant claim, or a non-compliant resource a Composition composes, is refused at admission, every policy names the controls it implements, every policy has a CI test proving it denies a violation, and PolicyReports are the evidence. CLAUDE.md said Kyverno ClusterPolicies. Kyverno 1.19, the current release, marks the kyverno.io/v1 ClusterPolicy deprecated in favor of CEL-based types, and its supported Kubernetes range ends at 1.35 while this cluster runs K3s 1.36.

Decision.

- ValidatingPolicy (policies.kyverno.io/v1beta1, the storage version; v1 is served but marked deprecated in this release) instead of ClusterPolicy. It is CEL, the language of Kubernetes ValidatingAdmissionPolicy and of the XRD rules already in this repository, and it keeps annotations, CLI tests, and PolicyReports. CLAUDE.md is updated to match. Kyverno v1.19.1 runs one minor version ahead of its supported Kubernetes range; that is accepted because every policy is proven on this cluster, not assumed to work, and recorded here.
- Ten policies, each annotated with platform.jordandesigns.io/control. They target what the XRDs cannot see. The XRDs already type sizes, environments, the cost-center shape, and digest-pinned images; the policies add the namespace rule, open cost centers, the ban on choosing a Composition directly, the GitOps-only write path, RBAC in team namespaces, the AWS internal-ingress refusal, and checks on what Compositions compose (public access, encryption at rest, TLS, cost tags), so a Composition bug cannot produce a non-compliant cloud resource either. restrict-pod-security and require-private-cluster-endpoint wait for xcluster.
- Every policy has a kyverno test suite under policies/tests with at least one resource that must pass and one that must fail: 37 cases, all passing. Neutralizing a policy's check in a scratch copy made its suite fail, so the tests discriminate. A policy-tests job in guardrails.yml runs them on every change with the CLI pinned to v1.19.1 and checked against its release checksum.
- Kyverno is bootstrap (make kyverno-install, chart 3.9.1): the admission controller and the reports controller only, since no policy uses generate, mutate-existing, or cleanup. The policies are synced by a platform-policies Argo Application without prune, like the XRDs, and the platform AppProject allows ValidatingPolicy, applied by make argocd-root rather than synced.

Leaks and trade-offs found while writing them.

- Cost allocation is spelled three ways: tags.CostCenter on AWS and Azure, labels cost-center on Cloud Run, and settings.userLabels.cost_center on Cloud SQL, because GCP labels allow no capitals and Cloud SQL keeps instance labels under settings. require-cost-allocation-tags carries all three paths.
- Encryption at rest is a setting only on RDS; Cloud SQL and Flexible Server cannot turn it off, so the rule is AWS-only. TLS on the AWS ALB is Terraform, outside admission.
- restrict-sizes cannot simply forbid compositionRef, because Crossplane writes the chosen Composition and revision onto the XR itself and Argo's server-side apply then carries them. The policy forbids them on create, allows Crossplane to set them, and on any other update requires them unchanged.
- require-review-source admits only the Argo application controller and Crossplane, which also blocks the kubectl annotate and apply a person used during earlier live tests. Server dry runs stay allowed, so the pre-merge check still works; break-glass is a PolicyException, itself a reviewed change.
- deny-internal-webservice-aws first looked up the per-session platform-aws-ingress EnvironmentConfig to see whether the internal ALB exists. The Kyverno CLI cannot mock a custom kind, so that path could never be tested in CI, and a per-session object is absent most of the time. The policy instead encodes the bootstrap default (internal ALB off) as a constant, which fails closed and makes enabling the internal ALB a reviewed change to both the Terraform variable and the policy.
- Every policy skips objects that are already being deleted. Found live: tearing down the evidence claim by git left it in foregroundDeletion, because Argo deletes with foreground propagation and the garbage collector finishes by updating the claim to drop that finalizer, as system:serviceaccount:kube-system:generic-garbage-collector, which require-review-source refused (the K3s log showed the GC sync error and the webhook rejection). Any policy would have done the same to a resource that failed it, leaving a deleted resource undeletable. An update to a terminating object only removes finalizers, so there is nothing to enforce; a not-being-deleted match condition on all ten fixes it, with a CLI case proving the garbage collector's update is skipped.
- One policy had a real bug the tests caught: in least-privilege-connsecret, a subject's namespace written as an escaped CEL field never matched, so a binding to another namespace's service account was admitted. Map indexing fixed it.

Live proof, 2026-10-02. Kyverno v1.19.1 ran on K3s 1.36 with the admission controller and reports controller, and Argo delivered all ten policies through platform-policies (PR #48). Every policy was enforcing at once (webhook configured), but eight reported not ready for reporting: Kyverno cannot grant itself read access to custom kinds, so the reports controller could not watch the claims, the composed resource kinds, or RoleBindings until the chart's reportsController.rbac.clusterRole.extraResources listed them; the policy status was then stale until the admission controller restarted, after which all ten were ready. A person applying a compliant Database for real was refused by require-review-source, naming system:admin as the caller, while a server dry run of the same claim was admitted, as was a GCP WebService with visibility internal. Server dry runs were refused for cost center cc-9999 (restrict-cost-centers), a claim in the default namespace (require-tags), a claim naming a compositionRef (restrict-sizes), and visibility internal on AWS (deny-internal-webservice-aws). A RoleBinding in team-demo to another namespace's service account was refused (least-privilege-connsecret) and one to its own was created. A claim delivered by Argo from a merged pull request (PR #49) was admitted, proving the allowed half of the GitOps rule, and with no GCP provider installed it composed nothing. The reports controller then produced PolicyReports by background scan: the claim passed require-tags, restrict-cost-centers, and deny-internal-webservice-aws, and the RoleBinding passed least-privilege-connsecret. require-review-source and restrict-sizes depend on the request (who wrote it, and the previous object), so they run at admission only; their evidence is the denials above rather than a report. The composed-resource policies were proven by the CLI suites; their live admission waits for the next session with providers installed.

Composed-resource policies, live, 2026-10-02. With provider-gcp-sql and provider-gcp-cloudrun installed (sql had been left out since Phase 4 and is now installed beside cloudrun, so GCP serves both paved-road types; PR #55), strict server dry runs of a DatabaseInstance and a V2Service shaped like the Compositions' output were admitted, and one violation at a time was refused by the policy that owns it: ipv4Enabled true or unset (deny-public-database), sslMode ALLOW_UNENCRYPTED_AND_ENCRYPTED or unset (require-tls-in-transit), and the Cloud SQL cost_center label missing or malformed, the Cloud Run cost-center label missing, or written as cost_center (require-cost-allocation-tags). RDS has no counterpart on GCP, so provider-aws-rds was installed with no provider config, which serves the CRD but cannot reach AWS: an Instance with storageEncrypted false or unset was refused by require-encryption-at-rest, publiclyAccessible true by deny-public-database, and no CostCenter tag by require-cost-allocation-tags, while the compliant Instance was admitted. A compliant Database and an internal WebService for team-data then went through GitOps (PR #54); Argo created both XRs nine seconds after the merge, Crossplane's writes of the composed DatabaseInstance, Database, User, and V2Service were admitted, and both XRs were READY and SYNCED in about ten minutes. GCP showed the instance with ipv4 off, ENCRYPTED_ONLY, and cost_center cc-1001, and the service with cost-center cc-1001 and internal ingress.

A leak found on that run: the composed resources had no PolicyReport. The four policies matched apiVersions "*", and the reports controller resolves each rule to a kind before it watches anything; it logged "failed to resolve kind for group sql.gcp.m.upbound.io, version *" for every composed kind, on every start, so it never watched them. Admission is unaffected, because the webhook passes the rule through as written, which is why every denial above worked. A restart changed nothing. An Audit-only probe policy naming v1beta1 for the two GCP kinds made reports appear at once for all three real policies on both resources; with the probe deleted and those reports cleared, they did not come back. The four policies now name v1beta1, the version every composed kind serves, with matchPolicy Equivalent so a request in a later served version is still matched through conversion (PR #55, 38 CLI cases still green). After Argo synced them, with no probe and no restart, the DatabaseInstance reported pass for deny-public-database, require-tls-in-transit, and require-cost-allocation-tags, and the V2Service pass for require-cost-allocation-tags, and the dry-run matrix gave the same results as before. So until this fix the composed-resource policies were preventive but produced no evidence, and the CLI suites could not have caught it, since kyverno test evaluates policies directly and never resolves kinds. Teardown by git (PR #56) held for one explicit prune sync (ADR-0018); the XRs and all four managed resources were gone in about two and a half minutes with no manual finalizer removal, GCP listed no Cloud SQL instance and no Cloud Run service, and the providers were removed.

Consequences. The control matrix in CLAUDE.md is the policy set, and each row is enforced at admission and proven in CI. Defense in depth: the XRD rejects malformed requests, the policies reject well-formed but non-compliant ones and anything a Composition gets wrong, the Composition fails closed where it cannot honor a field (ADR-0022), and cloud IAM is the last layer. Detective controls (ADR-0005) remain a separate, per-demo slice.

## ADR-0022: The WebService API exposes an image, a port, and reachability, and hides the runtime and the load balancer

Status: Accepted on AWS, GCP, and Azure through the full GitOps path (validated live 2026-10-02; AWS also by direct XR on 2026-10-01)

Context. Phase 4 adds the second paved-road type. A web service is far less symmetric across clouds than a database. ECS Fargate, Cloud Run, and Azure Container Apps differ in how traffic reaches them, whether they scale to zero, how they pull images, what names they accept, and which environment variables they reserve. Load balancers are the main cost line in ADR-0004, and ADR-0008 forbids per-claim network sprawl. CLAUDE.md also lists a repo and a pipeline in the goal, which needs GitHub write access well beyond the single-repository token in ADR-0019.

Decision. The xwebservice XRD (platform.jordandesigns.io/v1alpha1, kind WebService, namespaced) exposes intent only:

- image: a fully qualified reference pinned by digest. A tag is rejected at admission, because a tag can move after review and the image that runs would not be the one that was approved. Phase 5 adds a registry allowlist on top.
- port, at least 1024, because the container runs without root and cannot bind a privileged port. healthPath for load balancer and startup checks.
- size (small, medium, large), mapped to CPU and memory by each Composition. No CPU or memory figure appears in the XRD.
- maxInstances, 1 to 3. The lower bound is deliberately not exposed: Cloud Run and Container Apps scale to zero, while Fargate behind a load balancer cannot, because zero tasks means every request fails. The minimum is therefore zero where the runtime allows it and one on AWS. The visible difference is a cold start after idle on GCP and Azure, which is a recorded leak rather than a field.
- visibility, internal or public, default internal (ADR-0008). Internal means reachable only from the platform network.
- env, plain variables only, at most 20. PORT and names starting with K_ are rejected because Cloud Run reserves them. That is a GCP rule enforced on every cloud, the price of one API. Secrets are not accepted here.
- region, environment, owner, and costCenter, with the same rules as Database.
- status.url: the HTTPS URL clients call, whichever cloud produced it.

Hidden: the runtime, load balancers, target groups, listener rules, subnets, security groups, IAM roles, registries and pull mechanisms, log configuration, and revisions.

Names. The XR name keeps the 30 character rule from ADR-0015. ALB target groups and Container Apps cap names at 32 characters, less than idp-<namespace>-<name>, so those Compositions use the ADR-0021 pattern: a truncated readable part plus a short hash of the namespace and name, which stays deterministic for re-adoption (ADR-0010).

Delivery files. A WebService claim and its catalog entity are named <name>.webservice.yaml, so they never collide with a Database of the same name (Database names cannot contain dots). The pairing check from ADR-0019 works unchanged. The catalog entity is a Component of type service in a webservices System, because a running service is a Component in Backstage terms, not a Resource.

Runtime and ingress per cloud, proposed:

- AWS: ECS Fargate in the private subnets. One shared Application Load Balancer created in bootstrap, never one per claim; each WebService composes a target group and a host header listener rule. With no NAT (ADR-0008), image pulls go through ECR interface endpoints and an ECR pull-through cache, so the image must come from an upstream the cache supports. The provider role needs ecs and iam:PassRole added to its permissions boundary, with PassRole limited to one shared task execution role; per-service task roles stay out of scope because the boundary denies IAM writes. The listener and role ARNs embed the account ID, so they live in a bootstrap-only EnvironmentConfig, not the synced region map. The ALB and the endpoints bill hourly, so this bootstrap module is created and destroyed per demo session. An ALB has no certificate without a domain, which the other two clouds provide for free; how AWS meets the HTTPS contract is open.
- GCP: Cloud Run with its run.app HTTPS URL and no load balancer at all, so no standing cost. Internal visibility uses Cloud Run's internal ingress setting. Direct VPC egress into the platform subnet is the path to private databases later.
- Azure: Container Apps on one shared Consumption environment created in bootstrap, in its own subnet of the platform VNet, with the free azurecontainerapps.io HTTPS URL. Whether the environment is internal or external is a property of the environment rather than the app, which is a leak to confirm before the Composition is written. The environment's standing cost must be measured before it is left up. Both were confirmed; see "Azure, as built" below.

Deferred.

- databaseRef. Wiring a Database's Secret into a WebService would copy the password into a task definition or revision in plaintext. The right path is a cloud secret store, which is the External Secrets deferral in ADR-0002, so v1alpha1 has no secret input at all.
- Repo and pipeline scaffolding. Creating repositories needs a credential with administration write on all repositories, which discards the single-repository scope of ADR-0019, and every scaffolded repository's CI would draw on the same Actions minutes. The production credential is a GitHub App with short-lived installation tokens, which is browser-only setup. Phase 4 supplies images by reference; scaffolding is a later phase gated on the App and on CI capacity.

Consequences. A developer's request reads the same on every cloud, and the developer never sees a load balancer. The scale-to-zero difference, the reserved variable names, and the per-cloud name hashing are the visible costs of one API. Shared ingress keeps the load balancer at one per cloud, at the price of no isolation between services at the load balancer layer, the same trade ADR-0014 made for database networking. Each runtime's leaks are recorded against this ADR as its phase hits them.

AWS, as built (bootstrap/aws/ingress, crossplane/compositions/xwebservice-aws.yaml).

- Ingress. One internet-facing ALB in two ALB-only public subnets, HTTPS only with ELBSecurityPolicy-TLS13-1-2-2021-06 and a default 404, no port 80 listener. Hostnames are <name>.<team>.apps.jordandesigns.io: one certificate carries a wildcard per team, and one wildcard alias record per team points at the ALB, so a claim needs no DNS or certificate permission. A single *.apps wildcard with <name>-<team> labels was rejected because it is ambiguous (a-b in team c against a in team b-c) and an ALB routes duplicate host conditions to whichever rule has the lower priority, so one team could capture another's hostname. The cost is that onboarding a team on AWS is a diff to the ingress module's teams list. An internal ALB for visibility internal exists behind a variable that defaults off; with it off, an internal WebService fails in the Composition with a message naming the variable.
- Per-claim resources. A task definition (Fargate, ARM64 because Graviton is cheaper and the paved-road images are multi-architecture), a target group, a host-header listener rule, and an ECS service in the private subnets with no public IP, plus Usages so the target group outlives the rule and the service. Target group names cap at 32 characters, so they are idp-<ns>-<name> truncated plus an 8 character hash. Listener rule priorities must be unique per listener, so the priority is a checksum of namespace/name in 1 to 49999; a collision fails the second rule with PriorityInUse rather than shadowing the first.
- Image supply. The ECR pull-through cache fronts only ECR Public without credentials, so on AWS the image must come from public.ecr.aws; the Composition rewrites the reference to the cache and keeps the digest, and any other registry fails with a readable message. The XRD accepts any registry, so this is a per-cloud restriction the developer only meets on AWS. The cache creates repositories outside Terraform on first pull; make aws-ingress-clean deletes them before the module is destroyed.
- maxInstances is a ceiling only on AWS: one task always runs. Autoscaling up to the ceiling needs provider-aws-appautoscaling and application-autoscaling permissions, deferred.
- Identity. The provider's boundary gained ecs and a single iam:PassRole on the shared execution role; the phase4 policy scopes services, task definitions, and target groups by the idp- prefix and the Project tag and listener rules by the platform ALB names. iam simulate-principal-policy, 20 cases, all as intended: tagged creates on the prefix and rules on the platform listener allowed; untagged creates, other clusters, other prefixes, another ALB's listener, removing the Project tag, passing any other role or passing this role to any service but ecs-tasks, IAM writes, and ec2 writes denied.
- Per-session values. The listener ARNs, the execution role ARN, and the cache registry embed the account ID, and the task security group is recreated every session, so they live in the bootstrap-only platform-aws-ingress EnvironmentConfig that make aws-ingress applies from Terraform outputs; the synced region map holds only what outlives a session (VPC, private subnets, cluster, log group, domains).

A provider leak found live. The ECS Service referenced its target group through targetGroupArnSelector, as the listener rule does. In provider-upjet-aws v2.8.1 that reference crosses from the ecs provider to the elbv2 provider and never resolved: the Service stayed Synced=False with "referenced field was empty" while the target group was Ready with its ARN as the external name, the ecs provider's service account could list, get, and watch target groups, and restarting the ecs provider changed nothing. The listener rule, resolved inside the elbv2 provider, worked with the same selector. The Composition now reads the ARN from the observed target group and composes the Service, and its Usage, only once that ARN exists. Cross-provider selectors are therefore not relied on in this platform.

With bootstrap/aws/ingress applied (34 resources), team-demo/web-aws-a reached READY and SYNCED; the Service became Ready within seconds of the Composition fix and the ALB target was healthy about half a minute later. https://web-aws-a.team-demo.apps.jordandesigns.io returned 200 over HTTP/2 with a valid certificate, an unknown host on the same wildcard returned the default 404, and plain HTTP was refused. The task ran ARM64, 256 CPU units and 512 MiB, with a private IP only, pulling exactly the pinned digest through ecr-public/nginx/nginx-unprivileged. The service carried every required tag and logs reached /idp-platform/webservices/us-east. How the direct test ran ahead of the merge. Argo tracks main and the region map is synced, so the branch's map entries would have been healed away. The GitOps leg waits for the merge, which waits for CI.

AWS through GitOps, 2026-10-02. With bootstrap/aws/ingress applied again (34 resources in about three minutes), the Backstage WebService template, run for team-demo (default cloud aws), opened PR #40; it was server dry-run from the branch and merged on an all-pass, and team-demo/web-aws-b reached READY and SYNCED about three and a half minutes after the merge, the slowest of the three clouds because the ALB target must pass its health checks first. A leak that failed open, found on the same run. PR #41 changed web-aws-b to visibility internal while the internal ALB was disabled. The Composition refused, as designed, with a fatal result naming internal_alb_enabled, but a fatal result stops the pipeline, and Crossplane then keeps the composed resources it already had. The XR showed visibility internal and Ready True, with only Synced False, while the service stayed reachable from the internet with 200. A developer who asked for a service to be made private, and saw it Ready, would have believed it was. The same holds for any refused update on any cloud: the previous state stays live. Two layers fix it. First, xwebservice-aws now fails closed instead of failing: when visibility internal cannot be honored it leaves the listener rule and the ECS service out of the desired state, which deletes the route and stops the tasks, marks the target group not ready so the XR is not Ready, publishes no URL, and sets an IngressReady condition, False with reason InternalIngressDisabled and the remedy, on the XR (True with reason Routed otherwise). Rendered offline against a mocked running public service, the change to internal left only the target group and task definition desired, with Ready False and IngressReady False, while the unchanged public render kept all four resources, both Usages, the URL, and Ready True; every composed resource validated against the provider CRDs. Second, Phase 5 adds an admission policy that rejects visibility internal on AWS while the internal ALB is off, so the request never reaches the Composition. The general rule for the platform: a Composition that cannot honor a security-relevant field must fail closed by removing exposure, never fail and leave the old state.

GCP, a provider schema leak found on the first GitOps run, 2026-10-02. The Backstage template opened PR #26 for team-data/web-gcp-a, it merged on an all-pass, and Argo created the XR within seconds, which then stayed Synced=False with "containers[0].ports: expected map". A Cloud Run container exposes exactly one port, so provider-upjet-gcp v3.0.0 models ports as an object, while the Composition wrote a list as the Kubernetes container spec does. Nothing reached GCP: the apply of the composed resource is what failed. The offline render had passed, because crossplane render runs the functions but never validates their output against the provider CRDs. The XRD already exposes a single port, so the API is unaffected and the fix is in the Composition. The procedure gains a step: before a Composition change merges, a managed resource built from its template is server dry-run against the live CRD with strict field validation, which rejects both a wrong type and an unknown field (both were confirmed to fail).

GCP, an IAM leak found on the same run. With the Composition fixed, the V2Service failed its first observe with 403 on run.services.get for idp-team-data-web-gcp-a, although the role granting it was conditioned on exactly that prefix. The Data Access log shows why: the Cloud Run call carries an empty resourceAttributes, while Cloud SQL instance calls in the same project carry name and type, so a resource.name condition can never match a Cloud Run service. This is the ADR-0020 database and user leak again, on a different service. The Cloud Run service role is now granted unconditioned in the dedicated project. The scope that remains is the project, which holds only platform resources, plus the Composition, which always names services idp-<namespace>-<name> in the platform region. Region and prefix scoping move from IAM to the Composition and, in Phase 5, to admission. On AWS the same intent is still enforced by IAM, because ECS and ELB support resource ARNs with wildcards.

The create then failed on a second identity check: 403 on artifactregistry.repositories.downloadArtifacts for the ecr-public cache, with the provider service account as the caller of Docker-GetManifest. Cloud Run resolves the image digest with the deployer's credentials at create time, even though its own service agent performs the pull, so whoever deploys must be able to read the image. On AWS the ECS service carries no such check and only the task execution role reads ECR. bootstrap/gcp/web grants the provider Artifact Registry reader on that one repository.

GCP, as built (bootstrap/gcp/web, crossplane/compositions/xwebservice-gcp.yaml). One Cloud Run v2 service per claim, named idp-<namespace>-<name> (truncated with a hash past 49 characters), which is also its external name, so re-adoption is automatic (ADR-0017). No load balancer, certificate, or DNS: the run.app URL is the HTTPS endpoint, and the platform's standing cost on GCP stays at zero. Public sets ingress to all and disables the invoker IAM check, so reachability is decided by ingress alone, as the ALB decides it on AWS. Internal sets ingress to internal only. Every service runs as idp-webservice-runtime, which holds no role, never as the default compute account. Images come from public.ecr.aws through the ecr-public remote repository, the counterpart of the ECR pull-through cache, so one reference is valid on both clouds. Scaling is zero to maxInstances.

Azure, as built (bootstrap/azure/network, crossplane-auth, and apps; crossplane/compositions/xwebservice-azure.yaml). One container app per claim on one shared Container Apps environment. Five leaks shaped it.

- Standing cost. An environment injected into the platform VNet makes Azure create a managed infrastructure group that bills the customer: a Standard load balancer plus one static public IP for egress, and a second for ingress on an external environment, about $0.035 an hour or $25 a month together. AWS and GCP have nothing equivalent standing still (the ALB is per session; Cloud Run has no load balancer). An environment outside the VNet would cost nothing but would not be in the platform network. The environment is therefore per session, like the AWS ingress: bootstrap/azure/apps holds it and the image cache and is applied for a demo and destroyed after, while the delegated /27 subnet, the apps resource group, the runtime identity, and the Crossplane role stand at no cost. The infrastructure group is given a fixed name instead of Azure's ME_ default, because the budget filters on resource group names (ADR-0004) and would otherwise not see the load balancer's spend; the budget now lists it and the apps group.
- Visibility belongs to the environment. Whether apps can be reached from the internet is fixed when the environment is created, so one environment cannot serve both an internet-facing and a VNet-only app. The environment is external. A public WebService is an app with external ingress; an internal WebService is an app with external ingress off, which only other apps in the same environment can reach. That is narrower than "the platform network" on AWS and GCP, and it is the price of one environment rather than two.
- Image supply without internet egress. The documented egress for a workload profiles environment covers Microsoft's own registries only, so pulling from public.ecr.aws directly would need an outbound internet rule. Instead an ACR cache rule fronts ECR Public (a supported unauthenticated upstream on the Basic tier), the counterpart of the ECR pull-through cache and the Artifact Registry remote repository, and the subnet's default-deny NSG allows only Microsoft service tags (registry, Front Door first party, Entra ID, and the regional ACR and Storage tags). The Composition rewrites the image to the cache and keeps the digest; any other registry fails with a readable message.
- Identity. Container Apps pulls from a private registry with a managed identity attached to the app. The identity is a role-less id-idp-webservice-runtime whose only grant is AcrPull on the per-session cache, the counterpart of the GCP runtime service account. Attaching a user-assigned identity is authorized as assign on that identity, the Azure equivalent of iam:PassRole and actAs, so the provider holds assign on that one identity only. Its Container Apps role covers app lifecycle plus read and join on the environment, on the apps group only; the environment itself is Terraform's.
- Scaling and names. Apps scale from zero to maxInstances on the Consumption profile, like Cloud Run. Container app names cap at 32 characters, so long names use the ADR-0021 truncation and hash.

The offline check gap that let the Cloud Run ports bug through is closed for this Composition before any cluster is involved: crossplane resource validate checks the rendered container apps against the provider's published CRD, and it rejected both a list where the schema has an object and an unknown field when both were planted on purpose. The live strict server dry run remains the second check.

Replicas reached zero about five minutes after the last request, the default cooldown. The infrastructure group held one Standard public IP and one Standard load balancer, not the two public IPs the documentation lists for an external environment, so the measured standing cost while the session is up is about $0.03 an hour. ## ADR-0021: Postgres Flexible Server leaks into the Database contract, and Azure RBAC cannot scope by name

Status: Accepted (validated live 2026-09-30)

Context. Phase 3 writes xdatabase-azure against the same XRD and the same six-key Secret (ADR-0016). Azure differs from both RDS and Cloud SQL in naming, resource grouping, IAM, and networking, and provider-upjet-azure v2.7.0 has its own connection detail quirks.

Decision and the leak behind each part.

- Region. This subscription cannot create Postgres Flexible Server in eastus (az postgres flexible-server list-skus reports "Provisioning is restricted in this region"), so platform region us-east maps to eastus2 (ADR-0003).
- Global names. A Flexible Server name is a DNS label under postgres.database.azure.com, unique across all of Azure, 3 to 63 characters. RDS identifiers are unique per account and region, Cloud SQL names per project. The server name is idp-<namespace>-<name>, truncated to 54 characters, plus an 8 character SHA-256 prefix of subscription/namespace/name. It is deterministic, so re-adoption is automatic (the name is the external name), and two platforms using the same team and database names cannot collide. The readable part can be truncated for long names, so the hash, not the prefix, is what makes the name unique. The XRD did not change: the 30 character name rule from ADR-0015 still leaves room.
- Resource groups. Every Azure resource lives in a resource group, which neither AWS nor GCP has. Servers are created in one shared bootstrap group, rg-idp-platform-us-east-data, named in the region map, not one group per claim. A group per claim would need resource group write at subscription scope.
- IAM scoping. Azure RBAC cannot condition a create on a resource name prefix or a request tag, which is how the AWS role is scoped (ADR-0014) and how the GCP instance permissions are scoped (ADR-0020). The resource group is the boundary instead: a custom role with Flexible Server and database read, write, and delete, assigned on the data group only. Creating a server with private access is a linked authorization, so a second custom role grants subnets read and join, and privateDnsZones read and join, assigned on the delegated subnet and on the private DNS zone themselves. Custom roles accept only management group, subscription, or resource group assignable scopes, so that role is defined on the network group and assigned below it. The identity has no network write anywhere. Required tags cannot be enforced by RBAC on Azure; that moves to Kyverno at admission (Phase 5) and Azure Policy as the detective layer.
- Password generation. provider-upjet-azure offers autoGeneratePassword on FlexibleServer, as provider-upjet-aws does on RDS, so the platform password step GCP needs (ADR-0020) is not needed.
- Connection details. The provider publishes the username as login@servername, the format of the retired Single Server, which Flexible Server rejects. The Composition reads only the password from the provider's connection details and sets the plain login in the consumer Secret.
- Resource shape and deletion order. As on Cloud SQL, the application database is a separate FlexibleServerDatabase, which references its server through a selector on the composed FlexibleServer. A Usage with replayDeletion holds the server until the database is gone.
- Endpoint and port. Flexible Server reports an FQDN in the private DNS zone and no port. The endpoint is a DNS name again, which the XRD description already allows (ADR-0020), and the Composition sets port 5432.
- Defaults that are not the platform default. publicNetworkAccessEnabled defaults to true in the provider, so it is set false explicitly. Backup retention cannot go below 7 days, so Azure keeps backups where RDS keeps none and Cloud SQL has backups off; they are included in the server price up to the provisioned storage size. The smallest storage is 32 GiB, against 20 on the other clouds. TLS is enforced by the server default (require_secure_transport on), so no FlexibleServerConfiguration is composed; that resource is IdentifierFromProvider in this provider and would need a lookup on re-adoption.

- DNS. The FQDN the provider reports is <server>.postgres.database.azure.com, a public name that resolves through a CNAME into the linked private zone. The service writes the A record under a random label, not the server name. Inside the VNet the FQDN resolves to the private IP; outside it, it resolves to nothing usable. Clients must use the FQDN rather than the IP, because the IP can change on maintenance.

Live proof, 2026-09-30. team-demo/db-az-a reached READY and SYNCED about six and a half minutes after creation, with endpoint idp-team-demo-db-az-a-e2d38103.postgres.database.azure.com. db-az-a-conn held exactly the six keys, username app_admin and port 5432, and its password matched the provider's db-az-a-pgadmin Secret. The provider's own db-az-a-pgfs Secret carried username app_admin@idp-team-demo-db-az-a-e2d38103, confirming the Single Server format leak. Azure showed Postgres 17, Burstable Standard_B1ms, 32 GB, auto grow off, HA off, geo backup off, 7 day retention, public network access Disabled, the shared delegated subnet and DNS zone, require_secure_transport on, the app database, an A record at 10.80.1.4 in the zone, and every required tag. Azure placed the server in zone 2 without being asked; the provider's late initializer ignores the zone, so this caused no drift. A terraform plan of bootstrap/azure/network with the server live reported no changes, which proves that declaring the Storage service endpoint up front prevents the drift. Deleting the XR removed the database, then the server, then the DNS record, in about two minutes, with no manual finalizer removal.

Validated through GitOps, 2026-09-30. The Backstage Database template, run for team-ops (default cloud azure), opened PR #13 with the Azure Composition selected from the team annotation. After merge, Argo created team-ops/orders-az, which reached READY and SYNCED in about seven and a half minutes with the six-key Secret and owner guest. A forced reconcile left the password unchanged in all three Secrets. Teardown by git (PR #14) left the Application OutOfSync with "auto-sync will wipe out all resources" until one explicit prune sync (ADR-0018). The server was then gone in about two minutes, Argo returned to Synced, and no Crossplane-tagged resource remained in the subscription.

Consequences. The developer-facing API is unchanged. The Azure Composition is closer to the AWS one than to GCP (no password step) but keeps the GCP-style database resource and Usage. The provider identity is scoped by resource group rather than by name, which is coarser: inside the data group it could modify any Flexible Server, so nothing else may live there. Global names and the hash suffix make the cloud name less readable than on AWS or GCP; the Team and Database tags, not the name, are the reliable way to find a server.

## ADR-0020: Cloud SQL leaks into the Database contract in five places

Status: Accepted (validated live 2026-09-30)

Context. Phase 2 exists to find AWS assumptions in the xdatabase API. Writing xdatabase-gcp against the same XRD and the same six-key Secret (ADR-0016) exposed where RDS and Cloud SQL differ, both in the cloud model and in the provider implementation.

Decision and the leak behind each part.

- Password generation. provider-upjet-aws offers autoGeneratePassword on the RDS Instance; provider-upjet-gcp has no equivalent on the Cloud SQL User. The Composition therefore generates the admin password itself with function-go-templating, writes it to an internal <name>-sqluser Secret, and carries the observed value forward on every reconcile so it is generated exactly once. Verified live: the password hash was unchanged across a forced reconcile, and the consumer Secret's password matched the internal Secret.
- Resource shape. RDS creates the database and admin user inside the instance resource; Cloud SQL models them as separate Database and User resources that reference the instance by name. Both are composed with deletionPolicy ABANDON, because deleting the instance removes them and Postgres refuses to drop a role that owns objects.
- Deletion order. When an XR is deleted, Crossplane deletes every composed resource at once. On the first live teardown the instance went first, after which the provider's observe of the User returned instanceDoesNotExist as an error instead of reporting the user gone, and the User finalizer never cleared. The instance was confirmed deleted in GCP before the finalizer was removed by hand. The Composition now composes two Usages (instance used by database, instance used by user) with replayDeletion, so the instance cannot be deleted until its dependents are gone. AWS needed none of this because RDS is one resource.
- Endpoint and port. RDS reports a DNS hostname and a port; Cloud SQL reports a private IP and never reports a port. The XRD said the endpoint was a hostname, which was an AWS assumption, so the XRD description now says an address that may be a DNS name or an IP, and the Composition sets status.port and the Secret's port to 5432 itself. Fixed in the XRD per CLAUDE.md, not hidden in the Composition.
- Defaults that are not the smallest tier. Postgres 16 and later default to the Enterprise Plus edition on Cloud SQL, which rejects the shared-core tiers, so the Composition sets edition ENTERPRISE explicitly. TLS is enforced server side with sslMode ENCRYPTED_ONLY, matching the sslmode=require the Secret advertises and the RDS Postgres 17 default of rds.force_ssl.
- IAM scoping. Cloud SQL supplies resource.name to IAM conditions for instance permissions but not for database and user permissions: with a prefix condition on all three, users.create, users.list, and databases.get were denied on an idp- instance, as the Data Access audit log showed. Instance lifecycle stays conditioned on the idp- prefix; database and user lifecycle is granted unconditioned in the dedicated project. Separately, Cloud SQL answers 403, not 404, for databases and users of an instance that does not exist yet, so the first reconciles of a new Database look like permission errors until the instance is up.

Validated through GitOps, 2026-10-01: the Backstage Database template, run for team-data (default cloud gcp), opened PR #7 with the cloud resolved from the team annotation. After merge, Argo created team-data/orders-gcp, which reached READY and SYNCED with the six-key Secret (host 10.71.0.5) and every required label, owner guest. Teardown by git (PR #9) left the Application OutOfSync with "auto-sync will wipe out all resources" until one explicit prune sync (ADR-0018). The Usages then held the instance: the database and user were gone within seconds, the instance about three minutes later, and no finalizer needed manual removal.

Consequences. The developer-facing API is unchanged apart from a corrected endpoint description, and the six-key Secret is identical across clouds. The GCP Composition carries more machinery than the AWS one (a password step, two Usages, three managed resources instead of one), which is the cost of the uniform contract. The generated password lives only in Kubernetes Secrets, as on AWS (ADR-0002). Live proof, 2026-09-30: team-demo/db-gcp-a reached READY and SYNCED; db-gcp-a-conn held exactly the six keys with host 10.71.0.3; GCP showed POSTGRES_17, ENTERPRISE, db-f1-micro, ZONAL, 20 GB PD_SSD, backups off, deletion protection off, private IP only on the platform network and PSA range, ENCRYPTED_ONLY, and every required label.

## ADR-0019: Backstage runs slim on the laptop, and its GitHub access is a repo-scoped token

Status: Accepted (validated 2026-09-30)

Context. The Database template must render a claim and open a pull request on this repo, which needs GitHub write access. GitHub offers no CLI or API path to create a fine-grained token or a GitHub App without a browser step. Backstage also has to fit in the 4 GiB VM next to Crossplane and Argo (ADR-0010), and it is reached only through kubectl port-forward.

Decision.

- Backstage 1.55.2 (the upstream image, pinned) with in-memory SQLite and guest sign-in. The catalog, including the Database template and the team Groups, is rebuilt from git on every start, so losing the in-memory database loses nothing.
- GitHub access is a fine-grained personal access token limited to this repository, with Contents read and write, Pull requests read and write, Commit statuses read-only, and Metadata read-only, expiring in 30 days. It lives in ~/.config/idp-platform on the Mac and is loaded into the backstage namespace by make backstage-token; it is never committed. Commit statuses is required because Backstage's GitHub URL reader calls the commit status API to resolve a ref before fetching a template skeleton; without it the Render claim step fails with 403 while catalog reads still succeed.
- The template opens a pull request against the branch Argo syncs and never pushes to it, so a human review sits between the portal and the cloud.
- Owner comes from user.ref, not user.entity, because a user without a catalog entity (the guest) has an empty user.entity. The first run rendered spec.owner empty; the XRD rejected it on a server dry run, so the bad PR was closed without merging.

Consequences. Measured footprint is about 320 MiB, leaving roughly 1.1 GiB free on the VM. Every scaffolded claim is owned by guest until real sign-in exists; GitHub sign-in with a catalog User per developer is the production path and the right place to enforce that the requester belongs to the team they pick. The token is bound to a person and expires, so it must be rotated; a GitHub App with short-lived installation tokens is the production replacement and is deferred because it adds browser-only setup. Catalog entry per Database, added 2026-10-01: the template renders a Resource entity (type database, owned by the team's Group, with the cloud, the claim path, and the requester as annotations) into backstage/catalog/resources/<team>/ in the same pull request as the claim, and the catalog Location picks those files up with a glob. The entity lives in git next to the claim instead of being discovered from the cluster, so the catalog shows what was approved, not what happens to be running, and it needs no Kubernetes plugin or cluster credential in Backstage. The trade is that the entity does not show live status. A pre-commit hook and a CI job fail any change that leaves a claim without its entity, or an entity without its claim, so teardown removes both. Two catalog behaviors surfaced on the first teardown. A glob that matches no files is a read error in Backstage, and it failed the whole parent Location, which dropped the teams and the template from the catalog as soon as the last Database was removed; the glob now lives in its own Location (backstage/catalog/resources.yaml), so only that Location carries the error when there are no Databases. That was not enough on its own: a Location that fails to read keeps its previous entities, so the last Database's entity was never removed. The glob now always matches the databases System (backstage/catalog/resources/_platform/databases.yaml), which every Database Resource joins, so the Location always reads cleanly and a deleted entity file is orphaned and then deleted. And Backstage keeps an entity whose file is deleted, marked as an orphan, so the catalog is set to orphanStrategy delete.

Real sign-in needs a custom image, found 2026-10-02. A GitHub OAuth app now exists for sign-in (callback http://localhost:7007/api/auth/github/handler/frame, expiring user tokens, no device flow), with its client ID and secret in ~/.config/idp-platform beside the PAT. Wiring it showed that the upstream image cannot use it: ghcr.io/backstage/backstage is built from the create-app default template, whose backend registers only the guest auth provider and whose frontend is the bare new-frontend-system app, and Backstage's own release workflow describes the image as having no way to install additional plugins. App configuration cannot add a provider the image does not contain. The resolver the Backstage monorepo's development backend uses would also be the wrong one to copy: it issues a token for user:default/<GitHub username> without checking that the User exists in the catalog, so anyone with a GitHub account who reached the port would be signed in. The production path is therefore a platform-owned Backstage app, scaffolded with create-app into this repository, with the GitHub auth module and a resolver that requires a matching catalog User (and so rejects everyone else), a sign-in page offering GitHub, and an arm64 image built and published from the repository. That reverses the choice above to run the unmodified upstream image, and every Backstage upgrade becomes platform maintenance; it is scheduled as its own session. Until then sign-in stays guest and every claim is owned by guest.

The platform's own Backstage, 2026-10-02. backstage/app is a create-app 0.9.2 scaffold (Backstage 1.55) with three changes. The backend registers the GitHub auth provider and not the guest provider, so guest sign-in does not exist in the image at all. The GitHub provider uses the built-in usernameMatchingUserEntityName resolver, which signs a GitHub user in as the User entity of the same name and refuses anyone without one; no custom resolver code is involved, and catalog default behavior (dangerouslyAllowSignInWithoutUserInCatalog off) is kept. The frontend adds a sign-in page offering GitHub through the new frontend system's SignInPageBlueprint. People who may sign in are User entities in backstage/catalog/users.yaml, so granting portal access is a reviewed pull request; jordann6 is the first, a member of platform and the three teams, and claims are now owned by the requester rather than guest. Two supply-chain details surfaced. @yarnpkg/core 4.9.2, published on 2026-09-24 and pulled in transitively, declares a patch dependency on got that points at a file the package does not ship, so a fresh install failed in resolution; the app pins @yarnpkg/core to 4.9.1 through resolutions until a fixed release exists. And the vendored Yarn release that yarnPath requires is a third-party bundle that the repository's whitespace hooks would rewrite and its secret and GUID scanners flag (Yarn's public package-search key and help-text examples), so that one directory is excluded from the hooks and allowlisted by path in .gitleaks.toml; its content was checked byte for byte against the copy Backstage's template ships. Building and running: Docker cannot run beside the VM on this Mac (ADR-0010), so make backstage-build builds an arm64 image with the VM stopped, tagged with the git tree hash of backstage/app so the tag changes exactly when the app does and refuses to build from uncommitted changes; make backstage-image imports the saved image straight into K3s's containerd, and the chart runs it with pullPolicy Never, so no registry and no pull credential are involved. The OAuth app's credentials are a Secret loaded by make backstage-oauth from ~/.config/idp-platform. Publishing the image from CI to a registry is the production path and is deferred with the GitHub App. Two configuration leaks surfaced on the first deploy. The Helm chart starts Backstage with only its own ConfigMap (--config /app/app-config-from-configmap.yaml), never the image's app-config files, and the new frontend system refuses to render without app.title, which the upstream image had never needed; the title and organization name now live in the Helm values with everything else. And Helmet's default Content-Security-Policy includes upgrade-insecure-requests, which Safari applies to http://localhost, so every script was fetched over HTTPS from a port that only speaks HTTP and the page stayed blank; Chrome exempts localhost. Backstage is reached only over a plain-HTTP localhost port-forward, so that one directive is turned off. Live proof of the refusal, 2026-10-02: with the image deployed and before users.yaml reached main, signing in with the jordann6 GitHub account completed the GitHub OAuth flow and was then refused by Backstage with "Failed to sign-in, unable to resolve user identity", while /api/auth/guest/refresh returned 404, /api/auth/github/start redirected to GitHub with the OAuth app's client ID and the expected callback, and the catalog API answered 401 without a token. After users.yaml merged (PR #44) and one catalog refresh, the same account signed in. The first signed-in view then exposed a third configuration gap of the same kind: the new frontend discovers its plugins through app.packages, which also lived only in the image's config, so the root returned a 404 and the sidebar failed on the notifications API; app.packages: all and the catalog mounted at / joined the Helm values (PR #45), after which the full portal rendered with both templates. Running the WebService template as jordann6 opened PR #46 with owner jordann6 on the claim and requested-by jordann6 on the catalog entity, where every earlier claim said guest; the claim passed a server dry run, and the pull request was closed unmerged so nothing was provisioned. The resolver's refusal and acceptance are therefore both proven against a real GitHub account. Safari still renders a blank page after the CSP change, and its requests never reach the backend for the scripts; Chrome works, so this is recorded as an open browser-specific issue rather than a platform fault.

## ADR-0018: GitOps delivery with Argo CD, split into a platform project and team projects

Status: Accepted (validated 2026-09-30)

Context. CLAUDE.md makes GitOps the change-management control: every infra change is a reviewed commit that Argo syncs. Two risks are specific to Crossplane. Deleting an XRD deletes every XR of that type and, through them, the cloud resources, so an ordinary prune or a cascading Application delete could destroy every team's database. And Crossplane writes spec.crossplane fields and status onto every XR, which a client-side diff reports as permanent drift. The repo is also private, so Argo needs a credential, and Argo shares the 4 GiB VM (ADR-0010).

Decision.

- Install Argo CD slim: no Dex, no notifications, ApplicationSet at zero replicas, small requests. Server-side diff is on, so only the fields Argo applied are compared, and tracking is by annotation so Argo never adopts resources Crossplane composes.
- Two AppProjects. platform may manage only XRDs, Compositions, EnvironmentConfigs, Functions, DeploymentRuntimeConfigs, and Applications. teams may create only Database XRs and their own namespace, in team-* namespaces. A team folder therefore cannot create Secrets, RBAC, or raw managed resources, which enforces the paved road at delivery time before Kyverno exists.
- platform-apis syncs without prune, and the XRD carries Delete=false and Prune=false, so removing platform objects is a deliberate manual step. Team Applications prune, because deleting a claim file is the intended teardown.
- Providers and ProviderConfigs stay in bootstrap (make aws-provider), because they carry the cloud identity wiring from ADR-0001 and are installed per phase for memory.
- Repo access is a read-only ed25519 deploy key for this repo only, loaded from ~/.config/idp-platform by make argocd-repo and never committed. The initial admin Secret was deleted after install. Committing encrypted secrets (Sealed Secrets or SOPS) is deferred until a secret has to live in git.
- AppProjects are applied by make argocd-root rather than synced, so a bad commit cannot widen a project.
- Team Applications keep Argo's default refusal to auto-sync an app down to zero resources (allowEmpty off). A commit that empties a team folder, or a wrong branch or path, therefore cannot delete every Database the team owns. Deleting a team's last Database is one explicit prune-sync, triggered through the Application's operation field with kubectl, which Argo records with the initiating user. Validated in Phase 1: removing claims/team-demo/db-demo.yaml left the app OutOfSync with "auto-sync will wipe out all resources" until the explicit sync, which then deleted the XR and the RDS instance.

Consequences. The GitOps loop is the only path for claims, and the project boundaries mean a scaffolder bug cannot write anything but a Database. New teams need one Application each until ApplicationSet is enabled, which costs memory. Argo, the Backstage catalog, and the template PR target all track main since Phase 1 merged. If the repo becomes public the deploy key can be dropped. The AWS account ID is no longer committed: the ClusterProviderConfig role ARN and the Phase 0 verify bucket name are placeholders that make aws-provider and make aws-verify fill in from crossplane-auth Terraform outputs, and a pre-commit hook rejects any ARN carrying a literal account ID. History was rewritten on 2026-09-30 to replace the ID with ACCOUNT_ID in every earlier commit (Phase 0 is now 23c9545) and main was force-pushed; deployed infrastructure, Terraform state, and Argo were unaffected because nothing pins a commit. GitHub still serves the pre-rewrite commits through the pull request refs of PRs 1 to 4 until GitHub Support purges them, so that request is a precondition for making the repo public. A second rewrite on 2026-10-02 removed the Azure IDs (ADR-0011), after which every earlier pull request ref (PRs 1 to 37) points at pre-rewrite history, so the purge request covers all of them and the cached views of those commits.

## ADR-0017: RDS external names are assigned by AWS, so re-adoption is a lookup, not automatic

Status: Accepted. Amends ADR-0010.

Context. ADR-0010 says every Composition sets a deterministic external name, so a rebuilt control plane re-adopts cloud resources from the XRs in git. In provider-upjet-aws v2.8.1 the RDS Instance uses IdentifierFromProvider: its external name is the AWS DbiResourceId (db-XXXX), assigned at creation, and the human identifier is an ordinary spec field. The first Phase 1 attempt set the crossplane.io/external-name annotation to the identifier; the provider ignored it as a name, left identifier empty, and Terraform generated terraform-<random>. The IAM prefix scope from ADR-0014 denied CreateDBInstance, so nothing was created. That is the permissions design working as a guardrail, and it is the reason the identifier scope stays.

Decision. The Composition sets spec.forProvider.identifier to idp-<namespace>-<name> and leaves the external name to the provider. Which external-name strategy a resource uses is checked in the provider's config/externalname.go before its Composition is written, and each Composition's comment says which it is.

Consequences. The identifier is still deterministic, so a rebuilt control plane cannot create a duplicate: a fresh MR fails with DBInstanceAlreadyExists instead of orphaning a second billed database. Re-adoption becomes a manual lookup: read the DbiResourceId with aws rds describe-db-instances --db-instance-identifier idp-<namespace>-<name>, and set it as the crossplane.io/external-name annotation on the new Instance MR. Exercised 2026-10-01 against a simulated rebuild, which surfaced two more leaks. team-demo/db-readopt was created and reached Ready; its Instance MR was set to managementPolicies without Delete (Crossplane v2 namespaced MRs have no deletionPolicy), and the XR was deleted, which removed the XR, the MR, and all three Secrets while the RDS instance stayed available. Re-applying the same XR produced a new MR that failed with DBInstanceAlreadyExists, and only one instance existed, as designed. Setting the DbiResourceId as the external name then failed with AccessDenied on rds:AddTagsToResource: the provider stamps a crossplane-name tag with the MR's name, the rebuilt MR has a new generated name, and the role only allowed AddTagsToResource with a create-time Project request tag, which a tag-only change does not carry. The same denial would have hit any later Owner or Environment edit on a live database, so this was a latent Phase 1 bug. The role now allows AddTagsToResource and RemoveTagsFromResource on instances already tagged Project=idp-platform, while refusing to change the Project tag to another value or to remove it, so the role still cannot release an instance from its own scope (ADR-0014; verified with iam simulate-principal-policy in both directions). With that, the MR adopted the existing instance. Second leak: the rebuilt control plane generated a new master password, and because RDS never returns a password, the provider saw no drift and never sent it. The Database was READY with a connection Secret whose password RDS did not know, and nothing reported an error; CloudTrail showed no ModifyDBInstance from the provider. make rds-readopt NS=<namespace> NAME=<database> now does the whole procedure: look up the DbiResourceId, annotate the new MR, then push the generated password with modify-db-instance through a private temporary file rather than the command line. RDS logged "Reset master credentials", after which the Secret was valid, and deleting the XR removed the instance normally. Re-adoption therefore rotates the master password, which consumers must pick up from the Secret. Resources whose provider uses the name as the external name (for example the S3 Bucket in Phase 0) keep the automatic re-adoption ADR-0010 describes. This is a per-resource leak of the provider implementation into the platform's recovery story, and every new Composition must record which kind it is. GCP, Phase 2: DatabaseInstance, Database, and User in provider-upjet-gcp v3.0.0 all use their name as the external name, so xdatabase-gcp sets each explicitly and a rebuilt control plane re-adopts them automatically. Azure, Phase 3: FlexibleServer and FlexibleServerDatabase in provider-upjet-azure v2.7.0 also use their name, so xdatabase-azure sets both and re-adoption is automatic. FlexibleServerConfiguration is IdentifierFromProvider and is not composed. AWS is the outlier. GCP, Phase 4: the Cloud Run V2Service also uses its name, so xwebservice-gcp sets it and re-adoption is automatic. Azure, Phase 4: so does the ContainerApp, so xwebservice-azure sets it too.

## ADR-0016: The connection Secret is a platform contract, readiness waits for it

Status: Accepted for AWS, GCP, and Azure (validated live 2026-09-30)

Context. ADR-0009 composes the connection Secret in the function pipeline because namespaced XRs have no writeConnectionSecretToRef. Each cloud's provider publishes different connection keys (upjet RDS publishes its own names; Azure and GCP will differ again), so passing a provider's Secret through would leak the cloud into every consumer. A second problem surfaced in crossplane render: function-auto-ready marks the XR Ready once every desired composed resource is ready, so if the Secret is only composed after the password appears, the XR goes Ready before a usable Secret exists.

Decision. Every xdatabase Composition composes a Secret named <xr-name>-conn in the XR namespace with exactly these keys: host, port, username, password, dbname, sslmode. The XR's status.connectionSecret names it. The Secret is always composed and carries the go-templating ready annotation, set True only when host, port, and password are all present, so XR Ready implies a complete Secret. On AWS the provider also writes two internal Secrets in the same namespace: <name>-master (autoGeneratePassword output) and <name>-rds (the MR's own connection details, which is how the password reaches the pipeline).

Consequences. Consumers and the Backstage template depend on one Secret shape regardless of cloud. Three Secrets exist per AWS Database, two of them internal, all namespace scoped (least-privilege-connsecret). The password is still plaintext in Kubernetes Secrets; the External Secrets path in ADR-0002 remains deferred. crossplane render cannot mock composed connection details, so the password branch is only proven live. Live proof, 2026-09-30: Database team-demo/db-demo reached READY and SYNCED in about five minutes; db-demo-conn held exactly the six keys, its password matched the provider's db-demo-master Secret, and the endpoint resolved to a private 10.60.0.0/16 address. AWS showed db.t4g.micro, Postgres 17.9, 20 GiB gp3, not public, encrypted, single AZ, no backups, the shared subnet group and security group, and all required tags. GCP, 2026-09-30: the same six keys from xdatabase-gcp, with readiness additionally waiting for the Cloud SQL User to be Ready, because on GCP the password only works once the user exists on the instance (ADR-0020). Azure, 2026-09-30: the same six keys from xdatabase-azure, with the password from the provider's connection details (it writes <name>-pgadmin and <name>-pgfs, both internal) and readiness additionally waiting for the app database, so dbname is usable when the XR is Ready (ADR-0021).

## ADR-0015: XR names become cloud identifiers, so the XRD enforces the strictest naming rule

Status: Accepted

Context. ADR-0010 requires deterministic external names so a rebuilt control plane re-adopts cloud resources. On AWS the RDS identifier is idp-<namespace>-<name>, and RDS allows 1 to 63 characters, lowercase letters, digits, and hyphens, starting with a letter, with no double hyphens and no trailing hyphen. Kubernetes names allow dots, and up to 253 characters. Azure Postgres Flexible Server names must be globally unique DNS labels, and GCP Cloud SQL instance names cannot be reused for about a week after deletion. The cloud's naming rules leak into the platform API whether or not the XRD admits it.

Decision. The XRD carries a root CEL rule: a Database name is 1 to 30 lowercase letters, digits, or single hyphens, starting with a letter and not ending with a hyphen. With the idp- prefix, this leaves 28 characters for the namespace inside the 63 character RDS limit. Team namespaces follow the same rule by convention until a Kyverno policy enforces it in Phase 5.

Consequences. Developers see a naming error at admission instead of a cloud API error minutes later. The rule is stricter than any single cloud needs, which is the price of one API. Two leaks remain for later phases: Azure global uniqueness will need a suffix that is still deterministic (for example a hash of namespace and name), and GCP name reuse means deleting and recreating a Database with the same name can fail for a week. Both get recorded against this ADR when their phases hit them.

GCP, Phase 2. The Cloud SQL instance name is idp-<namespace>-<name>, and it is also the external name. Cloud SQL holds a deleted instance name for up to a week, so deleting a Database and recreating it with the same name in the same namespace fails for that period. This is documented Cloud SQL behavior and was not exercised live in Phase 2. Exercised 2026-10-01: team-data/orders-gcp, whose instance was deleted at 00:31 UTC, was requested again through the template and Cloud SQL accepted the same name at 03:07 UTC, about two and a half hours later, and the instance reached Ready. The hold is documented as up to a week, not a fixed week, so the platform cannot rely on reuse succeeding or failing; the rule stands and the gap remains documented. The platform does not work around it: a suffix would break deterministic re-adoption (ADR-0017), so the name rule stands and the gap is documented. Phase 2 used different names for the direct test (db-gcp-a) and the GitOps test for this reason.

Azure, Phase 3. Flexible Server names are unique across all of Azure, so the name is idp-<namespace>-<name> truncated to 54 characters plus an 8 character hash of subscription, namespace, and name (ADR-0021). The 30 character XRD rule did not need to change; the longest legal namespace and name render to exactly 63 characters. Name reuse was exercised 2026-10-01: team-ops/orders-az was deleted and requested again about twenty minutes later, and Azure created the same server name without complaint. Because the name is global, a freed name could also be claimed by anyone; the hash makes that practically impossible to hit by accident.

## ADR-0014: Database network attachment is shared bootstrap, not per claim

Status: Accepted for AWS (validated 2026-09-30)

Context. ADR-0008 puts networking in bootstrap and says each Composition implements the intent "reachable only from the platform network" in its own cloud primitive. On AWS that primitive is a security group plus an RDS subnet group. The obvious design gives every Database claim its own security group. That rule would be identical on every claim (tcp/5432 from the VPC CIDR), so per-claim groups add no isolation, while they require provider-aws-ec2 on the control plane (roughly 300 MiB on a 4 GiB VM, ADR-0010) and ec2 write permissions on the provider role.

Decision. bootstrap/aws/network creates one security group per engine (idp-platform-us-east-postgres: tcp/5432 from the VPC CIDR, no egress) and one RDS subnet group (idp-platform-us-east) across the private subnets. The xdatabase-aws Composition attaches every instance to both, reading their IDs from the platform-regions EnvironmentConfig, so the XRD never sees them. The provider role gets RDS instance lifecycle on the idp- identifier prefix only, with creation gated on aws:RequestTag/Project and changes gated on aws:ResourceTag/Project, and no ec2 write access at all.

Consequences. Smaller control plane and a smaller blast radius for the provider role. The trade is no network isolation between two databases inside the platform VPC: any workload in the VPC can reach any platform Postgres port, and authentication is the only barrier between tenants. If a tenant needs isolation from other tenants, the fix is per-claim security groups sourced from that tenant's workload group, which reintroduces provider-aws-ec2 and scoped ec2 permissions. Two IAM leaks surfaced while scoping the role: CreateDBInstance and ModifyDBInstance authorize against the subnet group, parameter group, and option group ARNs as well as the instance, so those ARNs are pinned in the policy and a new Postgres major version is a reviewed IAM diff; and the RDS service-linked role must already exist, because the permissions boundary denies all IAM. A third leak appeared on the first live reconcile: before it knows an instance's resource ID the provider looks it up by filter, so AWS evaluates DescribeDBInstances against db:* rather than the prefix. The policy grants that single read-only action on arn:aws:rds:us-east-1:<account>:db:*, not on *, and every write stays prefix and tag scoped. Validated with iam simulate-principal-policy: tagged create on the prefix allowed; untagged create, other prefixes, untagged deletes, other regions, other subnet groups, ec2 writes, IAM, and Aurora clusters denied.

Status: Accepted

Context. The Upbound registry (xpkg.upbound.io) now requires authentication to pull the official provider packages. Pulling them would put an Upbound account token on the control plane as a pull secret, which is a long-lived credential ADR-0001 exists to avoid, and ties the platform to a vendor account.

## ADR-0012: Cloud is assigned by team policy, not picked freely per resource

Status: Accepted (implemented in Phase 1, validated through GitOps on all three clouds by 2026-10-02)

Context. The goal says a developer picks a cloud. In real organizations developers rarely choose a cloud per database. The cloud follows from an acquisition, a data residency rule, a customer contract, or where the team's other workloads already run. Presenting cloud choice as a free per-request pick invites the interview question of why anyone would want it, and has no good answer.

Decision. Each team has a default cloud recorded on its Backstage group entity. The scaffolder template pre-fills the cloud from that default and hides the field unless the team is allowed to override it. The XR still carries the cloud as a label that selects the Composition, so the API does not change. Kyverno can later enforce that a namespace only creates XRs for its team's allowed clouds.

Consequences. The developer experience stays identical across clouds, which is the real promise. The multi-cloud value is framed as one platform serving teams that live on different clouds, which matches how platform teams actually operate. Adds a small amount of catalog metadata and one template conditional.

As built. Each team Group in backstage/catalog/groups.yaml carries the annotation platform.jordandesigns.io/default-cloud (team-demo aws, team-data gcp, team-ops azure). The Database and WebService templates look the team up with catalog:fetch and write that annotation into the claim's cloud label, so the Composition is selected from the team, never from a form field. Every GitOps proof ran this way: Databases for team-demo on AWS, team-data on GCP (PR #7), and team-ops on Azure (PR #13), and WebServices for team-data (PR #26), team-ops (PR #34), and team-demo (PR #40). Two parts of the decision are narrower than written. The templates have no cloud field at all, so there is no per-team override; a team that needs a second cloud today needs a second Group, and an override list on the Group is the extension point if one is ever needed. And no admission policy ties a namespace to its team's cloud: the cloud label on a claim written by hand into a team folder would be honored, so the binding is enforced by the template and by review of the pull request, not by Kyverno. Both are recorded as deliberate v1 scope rather than gaps in the paved road, since the template is the only supported way to write a claim.

## ADR-0011: Workload identity federation leaks per cloud, and the issuer lives in AWS

Status: Accepted (AWS and Azure validated 2026-09-30, GCP validated 2026-09-30 in Phase 2, Azure Postgres sub-provider validated 2026-09-30 in Phase 3)

Context. ADR-0001 federates the K3s service account issuer to all three clouds. Each cloud matches the Kubernetes identity differently. AWS IAM trust policies accept StringLike on the sub claim, so one role can trust every provider-aws service account with a wildcard. GCP Workload Identity Federation evaluates a CEL attribute condition, so a prefix match works. Azure federated identity credentials on a user-assigned managed identity accept only an exact subject, with a limit of 20 credentials per identity. Crossplane generates provider service account names that include the package revision, so exact matching breaks on every provider upgrade.

Decision. Give every provider a fixed service account name through a DeploymentRuntimeConfig serviceAccountTemplate, on all three clouds rather than only Azure, so the identity model is uniform. Keep the AWS and GCP trusts as tight as the Azure one where practical. The issuer's discovery document and JWKS are hosted on a private S3 bucket behind CloudFront with Origin Access Control (bootstrap/aws/oidc-issuer).

Consequences. Azure and GCP authentication depend on the AWS-hosted issuer being reachable. If CloudFront or the bucket is unavailable, new tokens fail to validate on every cloud. Accepted because the issuer is two static documents on a highly available CDN, and moving it (another CDN, a custom domain) only requires changing the issuer URL and republishing. Rotating the K3s service account signing key requires republishing the JWKS; caching is disabled on the distribution so the new key is served immediately.

A second leak surfaced during validation: in provider-azure v2, ResourceGroup is reconciled by the family provider itself, while in provider-aws every resource type lives in a sub-provider. So which pod carries the cloud identity differs per cloud, and the Azure family provider needs the token mount and a federated credential while the AWS family provider needs neither. The list of provider service accounts per cloud lives in each crossplane-auth module and must track which pods reconcile resources.

GCP, validated in Phase 2. The pool provider's attribute condition is an exact subject list (assertion.sub in [...]), so GCP is held to the Azure tightness even though CEL would allow a prefix. Two further leaks. First, GCP's default allowed audience is the full pool provider resource name, which embeds the project number; the pool instead allows a fixed audience (idp-platform-gcp-wif), so the DeploymentRuntimeConfig in git carries no project identifier, and the project number appears only in the generated ADC config. Second, the GCP family provider serves only ProviderConfig types and makes no cloud calls, so it gets a fixed name but no token, like AWS and unlike Azure. Each GCP sub-provider that reconciles resources needs its own exact subject in the pool condition and its own workloadIdentityUser binding, so installing a new sub-provider is a reviewed Terraform diff before it can authenticate.

Azure, Phase 3. provider-azure-dbforpostgresql reconciles FlexibleServer and FlexibleServerDatabase, so it gets its own fixed service account, its own projected token, and its own exact-subject federated credential, next to the one for provider-family-azure, which still reconciles ResourceGroup. Two of the twenty credentials per identity are used. Phase 4 adds provider-azure-containerapp, the third. The Azure subscription, tenant, and client IDs are no longer committed: the ClusterProviderConfig carries placeholders that make azure-provider fills from crossplane-auth outputs, the Terraform modules read the subscription from a gitignored terraform.tfvars, and a no-azure-ids pre-commit hook rejects any GUID other than the all-zero placeholder. Earlier commits contained the three IDs, all introduced by one Phase 0 commit and removed in Phase 3. None is a secret, but history was rewritten on 2026-10-02 anyway, the same treatment the AWS account ID had: git filter-repo replaced the three values with the all-zero placeholder in all 53 commits, the rewritten main's tree was confirmed byte-identical to the old one, and main was force-pushed; Argo resynced on the new head with nothing pinned to a commit. The old commits remain reachable through pull request refs until GitHub Support purges them (ADR-0018).

## ADR-0010: Control plane runs in a Lima VM on the MacBook

Status: Accepted (validated 2026-09-30). Amends ADR-0007.

Context. ADR-0007 assumes an always-on K3s control plane. No always-on host is available yet, and a cloud VM would add standing cost and put the platform brain inside one of the clouds it manages. The available host is an Apple M1 MacBook with 8 GB of RAM and limited free disk, which sleeps.

Decision. Run K3s in a Lima VM (Apple Virtualization framework, arm64 Ubuntu 24.04, 4 vCPU, 4 GiB, 20 GiB sparse disk) defined in bootstrap/k3s/lima and configured by the Ansible playbook in bootstrap/k3s/ansible. The VM has no host mounts so provider pods cannot see local cloud credentials, and only the Kubernetes API is forwarded to the Mac, bound to localhost. Install components by phase rather than all at once to fit in 4 GiB. Rules that follow:

- Never stop the VM or close the laptop while cloud resources exist. The Makefile refuses to stop or delete the VM while any Crossplane managed resource exists, and per-cloud budget alerts are the backstop.
- Every Composition sets deterministic external names on its managed resources, so a rebuilt control plane re-adopts existing cloud resources from the XRs in git instead of orphaning them. Amended by ADR-0017: where the provider assigns the external name (RDS), the Composition sets a deterministic identifier instead and re-adoption is a lookup.
- The same playbook targets an always-on host later. Moving hosts means copying the K3s service account signing key, or republishing the JWKS, and the cloud trusts from ADR-0001 keep working.

Consequences. Zero standing cost and fast iteration. Reconciliation pauses whenever the laptop sleeps, so drift correction and deletion only happen while it is awake. Backstage is not linkable between demos, which ADR-0007 listed as a benefit; that returns when the control plane moves to an always-on host. Memory is the binding constraint and will shape how many providers run concurrently. Measured at the end of Phase 0: K3s, Crossplane, provider-family-aws, provider-aws-s3, and provider-family-azure use about 2.3 GiB of the 4 GiB VM with one active managed resource type per cloud. The stop guard was tested by creating a Bucket and running make vm-stop, which refused. Phase 2 measurement: with provider-family-aws, provider-family-gcp, and provider-gcp-sql (provider-aws-rds and provider-gcp-storage removed for the phase), Argo, Backstage, and one live Cloud SQL Database, the VM used about 2.1 to 2.6 GiB. Docker Desktop cannot run alongside the 4 GiB VM on the 8 GB host, so crossplane render runs with the VM stopped (allowed only with zero managed resources). Removing a family provider has a second effect: Crossplane marks that provider's ClusterProviderConfig for deletion, held by the in-use finalizer until the provider returns. On reinstall the provider then finishes deleting it, so a config applied while it was still terminating silently disappeared (observed for GCP on 2026-10-01). Every make <cloud>-provider target now waits for a terminating config to be gone before applying a fresh one. The stop guard now fails closed: if the managed resource list cannot be read (a stale discovery cache after removing a provider produced exactly that), it refuses instead of counting zero. Phase 3 measurement: with provider-family-aws, provider-family-azure, and provider-azure-dbforpostgresql (both GCP providers removed for the phase), Argo, and Backstage, the VM used about 2.8 GiB. The Azure sub-provider used about 260 MiB and the family provider about 175 MiB. provider-family-aws still used about 355 MiB with no AWS sub-provider installed, so a phase that does not touch AWS could remove it too. Phase 4 measurement, 2026-10-01: provider-family-aws, provider-aws-ecs, and provider-aws-elbv2 settled at about 530, 510, and 500 MiB, well above earlier phases, and with Argo and Backstage left about 200 MiB available. Backstage (about 214 MiB) was scaled to zero for the direct WebService test and restored after, which left about 630 MiB. Two AWS sub-providers is the practical ceiling on this VM with Backstage running. The GCP leg, 2026-10-02, needed no such trade: provider-family-gcp and provider-gcp-cloudrun used about 194 and 185 MiB, and with Argo and Backstage both running the node stayed at about 2.5 GiB. The Azure leg, the same day, ran provider-family-azure at about 315 MiB and provider-azure-containerapp at about 197 MiB, and with Argo and Backstage the node used about 3.1 GiB of 4, tighter than GCP because the Azure family provider reconciles ResourceGroup itself and is the heavier of the two. The AWS GitOps leg was the tightest: provider-family-aws, provider-aws-ecs, and provider-aws-elbv2 at about 495, 538, and 565 MiB put the node at 92% with Backstage running, so Backstage was scaled to zero as soon as the template had opened its pull request (78% after) and restored for the catalog check after the providers were removed. The stop guard also met a state it treated as unreadable: with every provider removed, no CRD is in the managed category, so kubectl get managed fails with "the server doesn't have a resource type". That is not a stale cache; it proves there can be no managed resource. The guard now checks, when the list fails, whether any CRD carries the managed category, allows the stop only when none does, and still refuses in every other failure.

## ADR-0009: Crossplane v2 with namespaced composite resources

Status: Accepted

Context. The original design used Crossplane v1 claims and writeConnectionSecretToRef. Crossplane v2 makes namespaced composite resources (XRs) the developer-facing API and keeps claims only for legacy cluster-scoped XRDs. Namespaced XRs do not support writeConnectionSecretToRef. Upbound providers publish namespaced managed resources for v2.

Decision. Use Crossplane v2. XRDs are namespaced, and developers create XRs directly in their team namespace. Where this repo says claim, it means a namespaced XR. Connection details are produced by composing a Kubernetes Secret in the function pipeline, into the XR's own namespace. Only the managed resource types a phase needs are activated, which keeps CRD count and API server memory down on the small control plane (ADR-0010).

Consequences. Follows the supported model instead of a legacy path. Namespace becomes the tenancy and RBAC boundary for both the XR and its Secret, which strengthens the least-privilege-connsecret control. ADR-0002's mechanism changes from writeConnectionSecretToRef to a composed Secret; its External Secrets deferral stands. Kyverno policies match the XR kinds instead of claim kinds. Operational note from Phase 1: Crossplane v2 keeps a provider's deployment at zero replicas until at least one of its ManagedResourceDefinitions is active, so the MRAP must be applied before waiting for a new provider's pod.

## ADR-0008: Networking is a bootstrap concern, private by default, no per-claim NAT

Status: Accepted for AWS, GCP, and Azure (validated 2026-09-30).

Context. Networking is the largest leaky abstraction across the three clouds (AWS VPC and security groups, Azure VNet and NSGs, GCP VPC network and firewall rules are all modeled differently) and it is also a primary security and cost surface. Two failure modes to avoid: leaking cloud network primitives into the cloud-agnostic API, and letting each claim create its own VPC and NAT gateway, which is both sprawl and the main cost landmine from ADR-0004.

Decision. Networking lives in bootstrap, not in claims. Each cloud's bootstrap provisions one shared, private-by-default network (VPC, VNet, VPC network) with private subnets across the zones the platform-region map covers. Claims attach to it through the region map. The XRD never exposes CIDRs, subnet IDs, security groups, or any network primitive. The claim expresses intent only, for example reachable only from the platform network, and each Composition implements that intent in the cloud's own primitive.

Posture:

- Private by default. Databases and nodes get no public IPs. Cluster API server endpoints are private (ties ADR-0007). Managed resources are reachable only from within the platform network.
- Egress without per-claim NAT. Use private connectivity to cloud services (AWS VPC endpoints, Azure Private Link, GCP Private Service Connect) so managed resources reach cloud APIs without a NAT gateway. If a workload genuinely needs internet egress, use one shared NAT per cloud created in bootstrap and destroyed with it, never one per claim. (Resolves the ADR-0004 cost tension.)
- Default-deny firewalling. Security groups, NSGs, and firewall rules start default-deny and open only the specific ports a resource needs, source-restricted to the platform network. (CC6.6, CIS limit-network-exposure)
- Verification without public exposure. The database phase done-criteria (READY=True, connection secret exists) does not require the K3s control plane to reach a private database, so no public path is opened for verification. A true end-to-end connect test runs from inside the cloud network (a throwaway job in the provisioned xcluster or a bastion), not from K3s over the internet.

Consequences. Claims stay cheap and cloud-agnostic, no VPC or NAT sprawl, and the private-by-default posture maps directly to the compliance controls. The cost of shared bootstrap networking is that it is created and destroyed as a unit per cloud, so a demo cycle stands up the network with the first claim and tears it down after the last. The security-group versus NSG versus firewall-rule difference is a known abstraction leak: the XRD carries intent, each Composition carries the implementation, and each new leak gets its own note here. Marked Proposed until validated in the AWS phase, then updated to Accepted with the concrete endpoint and egress mechanism per cloud.

AWS, validated 2026-09-30 (bootstrap/aws/network): VPC 10.60.0.0/16 with two private /20 subnets in us-east-1a and us-east-1b, no internet gateway, no NAT gateway, and a route table holding only the local route and the S3 gateway endpoint. The default security group is adopted with zero rules. Egress mechanism: gateway endpoints only; RDS needs no endpoint because the provider calls the RDS API from K3s, not from inside the VPC. VPC flow logs (ALL traffic) go to CloudWatch with 7 day retention and the managed key, which avoids a standing CMK charge. Standing cost is $0 per month. Database attachment is shared bootstrap per ADR-0014.

GCP, validated 2026-09-30 (bootstrap/gcp/network): custom-mode VPC idp-platform-us-east with one subnet, 10.70.0.0/20 in us-east1, Private Google Access and flow logs on. The default internet route is deleted at creation, the GCP equivalent of having no internet gateway, and there is no Cloud Router or NAT. Egress mechanism: Private Google Access over a single route to private.googleapis.com (199.36.153.8/30), the stand-in for the AWS gateway endpoints. Firewall: explicit logged deny-all ingress and egress at priority 65534, with egress allowed only to tcp/5432 on the Private Service Access range and tcp/443 on the Google API range. Cloud SQL private IP comes from a Private Service Access range (10.71.0.0/20) peered to Google's service producer network. That peering is the GCP-specific leak: the database does not live in the platform VPC at all, and deleting the servicenetworking connection is refused for a while after a Cloud SQL instance is deleted, which would block deleting the network. The connection uses deletion_policy REMOVE_PEERING (google provider 8.1 and later), which removes the peering in that case so teardown completes. Unlike AWS, there is no per-engine security group to attach: Cloud SQL private IP instances are reachable from anything in a peered network, so the firewall rules govern what platform workloads may send, not what the database accepts. Standing cost is $0 per month.

Azure, validated 2026-09-30 (bootstrap/azure/network): VNet 10.80.0.0/16 in eastus2 in its own resource group, with one /24 subnet delegated to Microsoft.DBforPostgreSQL/flexibleServers. The subnet has default outbound access disabled, no route table, no NAT gateway, and no public IP, the Azure equivalent of no internet gateway. The private DNS zone privatelink.postgres.database.azure.com is linked to the VNet without auto-registration; Flexible Server with private access requires a zone ending in postgres.database.azure.com and writes each server's A record into it. NSG: Azure's built-in rules (AllowVnetInBound, AllowInternetOutBound) cannot be removed, so explicit deny-all rules at priority 4096 override them, and the only allows are the ones the service documents as required: tcp/5432 from the VNet into the subnet, tcp/5432 within the subnet, and tcp/443 to the regional Storage.EastUS2 service tag for WAL archival. Two Azure leaks. First, the service adds a Microsoft.Storage service endpoint to the delegated subnet when the first server is created, so Terraform declares it up front; otherwise the next apply would remove it and break WAL archival. Second, like GCP and unlike AWS, the database lands in a subnet that only the database service may use, so there is no per-engine security group to attach, and the NSG governs the subnet as a whole. Standing cost is about $0.50 per month for the private DNS zone, the first non-zero standing item in the platform network; VNet flow logs are deferred because they need a storage account and Network Watcher configuration with its own standing cost.

Amended for web ingress, 2026-10-01 (ADR-0022). A public web service needs an internet-facing load balancer, and on AWS that needs public subnets behind an internet gateway, which this network deliberately does not have. bootstrap/aws/ingress adds an internet gateway and two public subnets that hold only the shared ALB, with their own route table; the private route table is untouched, so nothing private gains a route to the internet. Tasks reach ECR and CloudWatch Logs through interface endpoints in one AZ plus the existing S3 gateway endpoint, still with no NAT. Because the ALB and the endpoints bill hourly, the whole module is created for a demo session and destroyed with it, so the network's standing posture between sessions is unchanged.

## ADR-0007: Control plane stays on K3s; EKS is a provisioned type, not the platform brain

Status: Accepted. Amended by ADR-0010 (K3s host is a Lima VM on the laptop, not always on).

Context. EKS was considered as the control plane that runs Backstage, Argo, and Crossplane. It is the most production-like option but has a standing control-plane cost of roughly $73/month per cluster that cannot be paused. The deeper problem is that the control plane is the platform brain: Crossplane's record of every cloud resource it provisioned lives inside the cluster as Kubernetes objects. Destroying that cluster while claims are live orphans billed cloud resources with no controller left to clean them up. It also forces a full Phase 0 re-bootstrap on every demo and leaves nothing running between demos.

Decision. Hybrid. K3s stays the always-on control plane at near-zero marginal cost, so the platform brain never dies, bootstrap is one-time, and there is no orphaning risk. EKS becomes a paved-road offering: a hardened xcluster type developers request and tear down per demo, following the additive-type pattern in ADR-0006. This gives a full production-grade EKS build and story without making the platform depend on it.

EKS hardening baseline for the xcluster Composition, mapped to the controls in the compliance section:

- Access via EKS access entries, not the aws-auth ConfigMap. Pods get AWS permissions via EKS Pod Identity or IRSA, never the node role. IMDSv2 enforced, hop limit 1. (CC6.1, CC6.3)
- Private API server endpoint, or public restricted to a CIDR allowlist. Nodes in private subnets, no public IPs. Default-deny NetworkPolicies. (CC6.6)
- Secrets envelope-encrypted with a customer-managed KMS key. (CC6.7)
- Bottlerocket nodes or Fargate; managed add-ons kept current; automated AMI patching. (CIS config hardening)
- Pod Security Standards at restricted, enforced by Kyverno: no privileged, no hostPath, drop capabilities, read-only root fs, runAsNonRoot. Image scanning and signature verification in CI. (CC7.1)
- All five control-plane log types to CloudWatch; GuardDuty EKS Protection on; kube-bench against the CIS EKS Benchmark. (CC7.2, evidence)

Mandatory teardown order for the xcluster (out-of-band AWS resources are created by Kubernetes, not Terraform, so order matters):

1. Delete all workload claims on the cluster and wait for Crossplane to confirm the underlying cloud resources are gone.
2. Delete Services of type LoadBalancer and confirm their ELBs and ENIs are removed.
3. Destroy the cluster.
4. Destroy the VPC and networking last.

Consequences. Platform survives teardown, no re-bootstrap tax, no orphaning risk, and Backstage stays live and linkable between demos. EKS spend accrues only while an xcluster is up and is destroyed with it. The platform does not run on EKS, which is a deliberate trade of maximum production fidelity for teardown safety and cost. Supersedes the option of running the control plane on EKS.

## ADR-0006: Escape hatch for resources the paved road does not fit

Status: Accepted

Context. The Upbound providers reach nearly the whole managed-resource surface of each cloud, but the platform only offers what has an XRD and Compositions. Some resources are one-off, or have no usable provider CRD, or would force a bad three-cloud abstraction. Trying to pave everything produces leaky XRDs that are worse than no abstraction.

Decision. Offer a curated paved road plus a documented exit. When a resource does not fit, drop out on purpose using provider-terraform to run an existing Terraform module as a managed resource, wrapped in a Composition so the claim experience stays uniform. Every escape-hatch use gets its own ADR naming why the paved road did not fit and what the exit costs in maintenance.

Consequences. Keeps the paved road opinionated and small. Preserves a uniform claim experience even for long-tail resources. Adds a second provisioning path to maintain, which is acceptable because it is bounded and documented. Interview line: a mature platform offers a paved road and a documented exit, not one or the other.

## ADR-0005: Compliance model is control enforcement, not certification

Status: Accepted

Context. The project should tell a compliance story without overclaiming. SOC 2 is an organizational audit over time by a licensed firm and cannot be a property of a portfolio platform. Claiming certification is an instant credibility loss.

Decision. Implement and enforce the technical controls a SOC 2 audit tests, and make the mapping explicit. Preventive controls are Kyverno ClusterPolicies that deny non-compliant claims at admission, each annotated with `platform.jordandesigns.io/control` naming the SOC 2 Common Criteria and CIS IDs it satisfies. Change-management control is GitOps: every change is a reviewed PR synced by Argo, the scaffolder opens a PR and never pushes to a synced path. Detective controls are cloud-native (AWS Config, Azure Policy, GCP Security Command Center), implemented as a slice for demos and destroyed after. Evidence is Kyverno PolicyReports. Start from CIS Benchmarks rather than a full framework.

Consequences. Compliance becomes a byproduct of the paved road: a developer cannot provision a non-compliant resource because the API will not allow it. The policy set doubles as the control matrix. Certification, org-level audit process, and full-framework coverage stay out of scope. Detective controls carry small per-evaluation cloud charges, so they run deploy-demo-destroy like everything else.

## ADR-0004: Cost containment, avoid always-on billed resources

Status: Proposed

Context. The control plane runs on the existing K3s cluster at near zero marginal cost. All cloud spend comes from resources a claim provisions. Some resources bill hourly whether or not they are used, and can quietly dwarf the databases: NAT gateways (~$0.045/hr plus data), cloud load balancers (~$16 to $25/mo each), zone-redundant HA (roughly doubles compute), and provisioned IOPS.

Decision. Compositions default to the smallest managed tier, skipFinalSnapshot and equivalents on, HA off, baseline IOPS. Databases are reachable without a per-claim NAT gateway; reuse existing networking or private connectivity that does not require one. The xwebservice load balancer is treated as the main cost line and destroyed with the claim. A small budget alert per cloud catches a forgotten always-on resource.

GCP budget, 2026-09-30 (bootstrap/gcp/budget): $10 per month on the billing account, filtered on the dedicated platform project rather than the project label. A label filter only sees spend on resources that carry the label, so one unlabeled resource would bill without tripping the alert; the project boundary catches everything because the platform owns nothing outside it. Alerts go to the billing account administrators.

Azure, Phase 3: B_Standard_B1ms with 32 GB is about $0.026 per hour while a server exists (about $19 per month if left up), and 7 days of backups are included up to the provisioned storage. The private DNS zone adds about $0.50 per month standing. The Azure budget used to filter on the Project tag, which has the gap the GCP budget avoids: an untagged resource would not count. Since 2026-10-01 it filters on the ResourceGroupName dimension instead, listing every group the platform owns (identity, network, data, and the Phase 0 verify group). The resource group is the Azure equivalent of the GCP project boundary, and the platform creates nothing outside those groups, so any spend there counts whether or not it is tagged.

Consequences. A single deploy-verify-destroy cycle across all three databases stays well under one dollar. Leaving one database up a full month is roughly fifteen dollars. The design forgoes production availability features by choice, which matches the out-of-scope list. Revisit before any resource is intended to stay up.

## ADR-0003: Platform region map instead of per-cloud region strings

Status: Accepted

Context. Each cloud names regions differently (us-east-1, eastus, us-east1). Accepting raw per-cloud region strings in the claim would leak cloud specifics into the cloud-agnostic API and break the promise that cloud choice does not change the developer experience.

Decision. The XRD exposes platform regions (for example us-east). A single platform-region map translates to the per-cloud region in each Composition. The map lives in one place via an EnvironmentConfig rather than being duplicated inside every Composition. Cloud SKU names and cloud region strings never appear in the XRD.

Consequences. Developers pick a platform region and get the right cloud region underneath. The map is the one place to maintain region coverage. Adds an EnvironmentConfig dependency to the bootstrap. Regions that do not exist in every cloud must be handled explicitly in the map, which is itself a leak to record when it happens.

Implementation, 2026-09-30: the map is the cluster-scoped EnvironmentConfig platform-regions (crossplane/environment/platform-regions.yaml), loaded into each Composition pipeline by function-environment-configs. Each platform region entry carries the cloud region plus that cloud's shared network attachment from bootstrap (ADR-0014), so bootstrap outputs reach Compositions without touching the XRD. The XRD's region field is an enum of platform regions and is immutable after creation; adding a region is one enum value in the XRD plus one map entry. Azure, Phase 3: this subscription is restricted from Postgres Flexible Server in eastus (az postgres flexible-server list-skus --location eastus returns "Provisioning is restricted in this region"), while eastus2 offers the Burstable tier and Postgres 11 to 18. us-east therefore maps to eastus2, the nearest allowed region and the same geography. This is the first recorded case of a platform region name not matching its cloud region name; the map, not the developer, absorbs it, and a support request for eastus access is the way back. The Azure entry carries resource group, VNet, subnet, and DNS zone names only; the subscription ID that turns them into resource IDs lives in a bootstrap-only EnvironmentConfig, platform-azure-subscription, applied by make azure-provider from Terraform outputs, alongside platform-gcp-project. GCP, Phase 2: us-east maps to us-east1 with no restriction. The Cloud SQL private network path embeds the GCP project ID, which is kept out of git like the AWS account ID, so it does not live in this synced map. make gcp-adc applies a second EnvironmentConfig, platform-gcp-project, from Terraform outputs; the GCP Composition loads it by reference next to the region entry and builds the network path from both. It lives in crossplane/providers/gcp with the rest of the bootstrap-applied identity wiring, outside every path the platform-apis Application includes. A first copy under crossplane/environment/bootstrap was matched by the environment/*.yaml include, which in Argo also matches subdirectories, so Argo synced the placeholder and self-healed the live object back to it; the first GitOps Database then failed its create with a malformed project ID and nothing was provisioned. Moving the file and removing Argo's tracking annotation from the live object fixed it.

## ADR-0002: Connection secret handling and the External Secrets deferral

Status: Proposed. Mechanism amended by ADR-0009: the Secret is composed in the function pipeline, not written via writeConnectionSecretToRef.

Context. Crossplane writes connection details to the claim namespace via writeConnectionSecretToRef. That means plaintext database credentials sit in a Kubernetes Secret. Acceptable for a demo, weak for a production-mimicking story, and a predictable interview probe.

Decision. For the initial phases, keep writeConnectionSecretToRef with RBAC scoped so only the claim namespace can read the secret, and a Kyverno policy keeping connection secrets in-namespace. Record External Secrets Operator as the intended production path: sync connection details into each cloud's secret manager and back, so no long-lived plaintext credential is the source of truth. Implement or explicitly defer ESO, and note which in this ADR when decided.

Consequences. Fast to ship, honest about the tradeoff. The gap between the demo path and the production path is written down rather than hidden, which is the stronger interview position. If ESO is deferred past the compliance phase, revisit against ADR-0005 (CC6.1 access control).

## ADR-0001: Provider authentication and bootstrap secret storage

Status: Accepted (AWS and Azure validated 2026-09-30, GCP validated 2026-09-30 in Phase 2)

Context. The K3s cluster lives outside all three clouds, so Crossplane needs a way to authenticate to each of them. Long-lived plaintext cloud keys in a Secret, or worse in git, is the single biggest credibility gap for a platform that claims to mimic production. The first draft preferred AWS IAM Roles Anywhere, Azure federated service-principal credentials, and GCP Workload Identity Federation. Roles Anywhere turned out to be a poor fit: the Upbound provider-aws ProviderConfig has no Roles Anywhere credential source, so it would need aws_signing_helper in a custom provider image or sidecar, plus a private CA whose key still has to be stored somewhere.

Decision. Make K3s its own OIDC issuer and federate that one issuer to all three clouds. K3s signs projected service account tokens with a public issuer URL (a private S3 bucket behind CloudFront, ADR-0011), and the discovery document and JWKS are published there. Each cloud trusts the issuer:

- AWS: IAM OIDC provider plus a role assumed with AssumeRoleWithWebIdentity. ProviderConfig source IRSA, with the projected token and role ARN injected by a DeploymentRuntimeConfig.
- Azure: user-assigned managed identity with federated identity credentials. ProviderConfig source OIDCTokenFile.
- GCP: Workload Identity Federation pool and OIDC provider, impersonating a service account. The external_account credential config holds no key material. The project enforces iam.disableServiceAccountKeyCreation.

No provider credential is a secret, so SOPS or Sealed Secrets is not needed for provider auth; it is still required later for Argo repository credentials and the Backstage GitHub token. Provider IAM is least privilege: Phase 0 grants only what the verification resources need, and each phase adds exactly what its Compositions manage, as a reviewed diff. AWS permissions sit under a boundary that denies IAM changes and regions other than us-east-1. No cloud resource is created before its ProviderConfig is verified with a trivial managed resource that reaches Ready.

Consequences. No long-lived cloud credential exists anywhere in the platform runtime, and one issuer gives a uniform identity story across three clouds. The human bootstrap path (Terraform run from the laptop) still uses a local IAM user, which is out of scope for the platform runtime and recorded here so it is not overlooked. Rotating the K3s signing key means republishing the JWKS. Validation, 2026-09-30:

- AWS: provider-aws-s3 assumed idp-crossplane-provider-aws through AssumeRoleWithWebIdentity (CloudTrail userName system:serviceaccount:crossplane-system:provider-aws-s3). A namespaced Bucket reached SYNCED and READY and was deleted cleanly. IAM simulation allows CreateBucket only on the verification prefix and denies other buckets, RDS, and IAM. The ProviderConfig uses source WebIdentity with a Filesystem token rather than IRSA, so the role ARN is explicit in the ProviderConfig instead of hidden in pod environment variables.
- Azure: provider-family-azure authenticated with source OIDCTokenFile against a user-assigned managed identity. A namespaced ResourceGroup reached SYNCED and READY with the required tags and was deleted cleanly.
- The cluster holds no cloud credential Secret, and no provider pod has an access key or client secret in its environment.
- GCP (Phase 2, bootstrap/gcp): a dedicated project with Data Access audit logs on, a workload identity pool trusting the K3s issuer, and a service account the federated principals impersonate. The project enforces iam.disableServiceAccountKeyCreation (and sql.restrictPublicIp as defense in depth for deny-public-database). The ClusterProviderConfig uses source InjectedIdentity, so authentication falls to Application Default Credentials, which read an external_account config from the idp-gcp-adc ConfigMap. That config holds only the token file path, the STS audience, and the service account to impersonate, so it is a ConfigMap rather than a Secret, generated by make gcp-adc from Terraform outputs. provider-gcp-storage created a namespaced Bucket that reached SYNCED and READY and was deleted cleanly. The Data Access audit log shows the caller as the provider service account with principalSubject system:serviceaccount:crossplane-system:provider-gcp-storage. A Bucket outside the idp-verify- prefix failed with 403 on storage.buckets.create, which is the IAM condition working.
- GCP key denial, exercised 2026-10-02: creating a key for the provider service account and for the web service runtime account was refused for both with FAILED_PRECONDITION, "Key creation is not allowed on this service account", citing constraints/iam.disableServiceAccountKeyCreation, and the Admin Activity log recorded both CreateServiceAccountKey calls with status 9. The caller was a project owner, so the organization policy held against full IAM rights, which is the point of enforcing it as policy rather than relying on who has iam.serviceAccountKeys.create. Neither account holds a user-managed key. gcloud writes its output file before calling the API, so a refused request still leaves an empty key file behind; the check that matters is the key list in GCP, not the file.

Accepted for all three clouds.
